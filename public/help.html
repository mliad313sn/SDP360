1Overview

The Endeavour Mining IT Operations Dashboard is a web-based platform that centralises IT service-desk data from ManageEngine Analytics Plus and provides real-time KPIs, site reporting, executive exports, inspection logs, meeting records, and AI-assisted analysis for all Endeavour Mining sites.

As of May 2026, the platform covers eight main areas:

  • Main Dashboard (§3) — live helpdesk KPIs, group/week filtering, ageing and open-ticket tracking
  • Site Reports (§4) — weekly submission forms filled by on-site IT teams
  • Report Builder (§5-6) — one-click PPTX exports for weekly and monthly reviews + monthly board deck runbook
  • Activity Tracker (§10) — 31 activities × 4 pillars × 10 sites, monthly scoring
  • IT Inspections (§11) — site infrastructure inspections with checklist, photos, signatures, PPTX export
  • Meetings & Council Escalations (§12) — monthly PV (Procès-Verbal) digital twin + Mine IT Council view
  • Executive Scorecard (§13) — consolidated 5-tab view for management (KPIs, Action Plan, Tech Scorecard, Change & Incidents, Customer Voice)
  • AI Analysis & Insights (§14) — on-premise LLM commentary (Ollama / Mistral Nemo) + Analyze Lite (deterministic, no network)
ℹ️ Ticket data is sourced from ManageEngine Analytics Plus via OAuth (MEAplus scope). The dashboard syncs automatically every hour. All dashboard pages serve from a local SQLite cache for instant load; Zoho is only contacted by background sync jobs.

2Accessing the Dashboard

Open your web browser and navigate to the server address provided by your IT administrator (e.g. http://<server-ip>:3456). A login screen will appear.

  1. Enter your username and password as provided by the administrator.
  2. Click Sign In.
  3. You will land on the Main Dashboard. The navigation header provides links to all sections your role can access.
💡 Bookmark the URL so you can return quickly. If you are accessing via RDP, the dashboard works in any browser on that machine. Your session stays active for 24 hours — no need to sign in again each day.

Changing your password

Any user can change their own password at any time from the Site Reports page. Click the 🔑 icon next to your username in the top-right corner, enter your current password and a new one (minimum 8 characters), then click Change Password.

3Main Dashboard

The main dashboard (IT Operations Center) displays real-time helpdesk metrics pulled from Zoho Desk.

3.1 Filters & Week Picker

The filter bar at the top of the page controls what data is displayed:

  • Week picker — use the ◀ ▶ arrows to navigate between weeks. Weeks follow the Zoho Sunday-start convention (W01 = first Sunday of the year, each week runs Sunday–Saturday).
  • Group selector — click the group name chip to filter tickets for a specific IT group (e.g. Operations, Application, Network…). Click again or select "All Groups" to reset.
  • Preset buttons — quick shortcuts to common group combinations saved per user in the browser.
  • View toggle — switch between Summary, Detail, and Ageing views.
⚠️ Week numbers in the dashboard match Zoho Analytics Plus week numbering. If a week label looks off, always verify against the Zoho AP calendar rather than standard ISO weeks.

3.2 KPI Cards

The top row of cards shows the key metrics for the selected week and group filter:

3.3 Ageing Tickets

The ageing panel shows open tickets grouped by how long they have been waiting. Tickets are colour-coded: Green = 0–3 days, Amber = 4–7 days, Red = 8+ days.

Click any row to drill down and see the individual ticket details pulled from Zoho.

3.4 Data Sync

Data is refreshed automatically but you can trigger a manual sync at any time:

  • ⟳ Refresh — reloads the page from the browser cache (fast, no new Zoho query).
  • ⚡ Force Sync — clears the server cache and fetches fresh data from Zoho immediately. Use this after a large batch of tickets has been updated.
ℹ️ Automatic sync schedule: every 4 hours at :45 past the hour, plus explicit triggers at 06:00, 13:00, and 16:00 on workdays.

3.5 Risk Register Export

In Monthly view, a 📥 Export Risk Register button generates the monthly Occurrence sheet (.xlsx) for the operations Risk Register. Aggregates incidents per site × per risk domain (5 domains: Internet, Mobile, Power, Infrastructure, Radio).

  • Picks up the currently selected month from the period picker (Monthly view required — weekly is blocked because months can straddle weeks).
  • Excludes Individual-scope tickets (single-user issues) and the Inspection category.
  • Output filename: RiskRegister_Occurrence_YYYY-MM.xlsx, opens in Excel / LibreOffice / Keynote.
  • Layout matches the existing monthly Occurrence sheets — column B is the site code, column I is the Occurrence count.
💡 Diagnostics: after clicking the button, browser DevTools Console shows [risk-register] diagnostics with per-category skip counts. skipped_unknown_site > 0 means a SDP site label isn't mapped — super_admins can add the mapping at Admin → Risk Register codes.

4Site Reports — Weekly Workflow

Click 📋 Site Reports in the header to access the weekly reporting module. Each site IT team submits one report per week covering infrastructure KPIs, helpdesk metrics, highlights, and action items. The monthly PPTX is automatically built from these weekly submissions.

4.1 Infrastructure KPIs

Fill in Section 1 — Infrastructure KPIs with this week's actual values for each monitored system (WAN uptime, server availability, backup success rate, etc.).

  • Click 📋 Copy from Previous Week to pre-fill all rows from last week's report. The Service name, KPI name, Target and previous Status/Trend are carried over — the Current Value column is intentionally cleared so you type only this week's numbers. The previous week's value is kept in memory to compute the Trend automatically.
  • Once you type a numeric value, the Status (🟢/🟡/🔴) is set automatically by comparing the value to the Target, and the Trend (▲/→/▼) is set by comparing the value to last week's value — no manual selection needed.
  • For non-numeric entries (e.g. "N/A", "OK", text), auto-computation does not apply. Set Status and Trend manually for those rows.
⚠️ Manual Status / Trend values are overridden at PPTX export time for numeric rows. Even if you manually set a Trend in the form and save the report, the PPTX generator will recompute the Trend from the actual values (current vs previous week). The slide will show the computed direction — not what you typed. For non-numeric rows with no previous value to compare, the saved manual value is preserved.
💡 Copy from Previous Week is the recommended starting point every week — it saves the most time for sites with long KPI lists.

Click ⚡ Fill from OPManager / Meraki to auto-fill empty Current Value cells from live monitoring for this week (WAN1/WAN2 from Meraki, LAN/WLAN/Servers from OPManager). It never overwrites a value you typed. Hover any auto-filled number to read how it was measured.

💡 WAN availability is event-based. The WAN1/WAN2 numbers come from the outage log — the uplink status Meraki records every 5 minutes, aggregated over the report week — not from packet-loss (a fully-down link reports 0% loss, so loss cannot measure uptime). This is our own OPS measurement and it matches the WAN Health dashboard. In line with Meraki's own method, whole-device / power outages (the box offline) are excluded from the denominator — only per-ISP link outages reduce the number. It is not Meraki's official "% Time Up" from the Summary Report, which Meraki does not expose through any API. If the WAN poller has not run yet, WAN cells stay blank rather than show a fabricated number — type the value manually or wait for the poller.

4.2 Helpdesk Metrics

Section 2 — Helpdesk Metrics is pre-populated from Zoho data for your site's group. Review the auto-filled numbers, make any manual adjustments if needed, and save.

The Tech Break Pool panel lets coordinators mark which technicians are on break. Click a chip to add them; click again to remove.

4.3 Low / High Lights

Enter only the issues and successes that occurred this specific week. Do not copy items from the previous week — the system collects all weeks automatically and the monthly report will include every week's entries.

  • ▼ Issues & Incidents: problems, outages, or degraded services that happened this week.
  • ▲ Successes & Achievements: completions, improvements, or positive outcomes this week.
  • Changes In Progress / Pending: active or upcoming change requests. Enter a change once when it starts — do not re-enter it every week.
⚠️ If you repeat the same item every week, it will appear only once in the monthly PPTX (deduplicated automatically), tagged with the first week it was entered. Enter each item only once.

4.4 Action Items

List tasks that require follow-up this week. Do not re-type an action that is already being tracked — carry it forward and update its Status (open → in progress → closed).

  • Automatic carry-over — when you open a blank week, the unresolved actions of the previous week are pre-filled as a draft (banner "↩ N action(s) carried over"). Review owner, due date and status, then Save; Undo removes them.
  • ↵ Import open actions from a previous week — pick a week, then tick the actions to bring in. An action that cannot be imported is greyed out with the reason: already in this report (saved or just typed), closed since in Wxx, cancelled or closed. The week list counts only the actions you can really import.
  • Group code — every action carries a coloured badge #CODE and "tracked since Wxx · N wk". All the weeks of the same action share the same code; two actions with similar titles but different codes are two different actions. Hover the task cell to see the code.
  • ⚯ Fusionner des doublons (merge duplicates) — tick two or more actions of the site (all weeks) that are really the same: the newest one wins, the others take its group code and its title. The whole group moves (every older week too), so an old copy can no longer come back as open. Duplicates that already exist are not merged automatically — merge them once.
  • Cancelling an action asks for a justification (the same window as the meeting statuses); it is added to the action's Comment as "Cancelled: …". Changed your mind? Set the status back — or use the Site Actions hub (12.9).
ℹ️ The monthly PPTX shows each action once, with its most recent status across all submitted weeks. If the same task appears in week 1 as "open" and in week 4 as "closed", the PPTX will show it as closed. Duplicate entries across weeks are automatically removed.
⚠️ Do not create a new action item for something that already exists — even if it is still open. Use Import open from previous week to bring it forward, then update the status. Creating duplicates will result in the same task appearing twice in the monthly report.

4.5 Submitting a Report

  1. Complete all four sections (Infrastructure, Helpdesk, Lights, Action Items).
  2. Review the summary at the top of the page.
  3. Click the green ✅ Submit Report button.
  4. A confirmation banner confirms the report is submitted. The status changes to Submitted.
⚠️ Once submitted, a report can only be re-opened by an Admin. Make sure all information is correct before submitting.

4.6 Parc informatique (asset follow-up)

Tab 5 · Parc informatique shows four counts for your site, computed for the report week: hardware without a QR code (empty Barcode / QR code field — the whole fleet, not just the week's arrivals), without acquisition date, without purchase cost and not assigned to a user (all four for In Use / In Store / In Repair). The daily alert still reports the day's new hardware without a QR code. Each count shows the change versus the previous week's report. The tab shows counts only — the detailed lists go to your site's asset manager in the reminder e-mails.

Two optional notes: Traité cette semaine and Plan / blocages. They save automatically. The counts are frozen when you submit and appear in the weekly e-mail with your notes; an empty note appears as a highlighted amber non renseigné tag. In that e-mail the Parc informatique block (violet header) shows counts only, with no link into Assets. Submit is never refused, it only warns you.

ℹ️ A site with no hardware in the register (e.g. Exploration, Tanda) shows "Aucun matériel rattaché à ce site" and the tab counts as done. Auto status now works: once the five tabs are done the report becomes Ready — you still have to click Submit.

5PPTX Report Generation

Weekly PPTX (single site)

On the Weekly tab, select your site and week, then click ⬇ Weekly PPTX. The file covers Infrastructure KPIs, Helpdesk Metrics, Lights, and Action Items for that one week.

Monthly Site Report

On the Monthly tab, select your site and month, then click ⬇ Export PPTX. The file summarises the full month across all submitted weeks.

The monthly PPTX is built automatically from weekly data. For best results, review the consolidated Lights and Actions before generating:

  1. Load the Monthly Report for your site.
  2. Check the Low/High Lights and Action Items tabs — the system auto-merges all weeks and removes duplicates.
  3. Edit or remove any entry that is not relevant at the monthly level.
  4. Click 💾 Save Monthly Edits to lock in your curated version.
  5. Click ⬇ Export PPTX — the saved edits will be used; the auto-merge fallback is only used if no edits have been saved.
⚠️ If a new weekly report is submitted after you saved Monthly Edits, the saved edits are not automatically updated. You will need to return to the Monthly Report tab, review the merged content again, and click 💾 Save Monthly Edits once more before exporting. Always save edits as the last step, just before exporting.

Regardless of what values are stored in the weekly report form, the following are always recalculated at export time:

Combined All-Sites Monthly PPTX (Admin only)

Click ⬇ Export ALL Sites PPTX in the Monthly tab to generate one file covering all active sites for the selected month. Each site gets a divider slide followed by its 6 report slides. Ideal for the monthly management meeting.

Weekly All-Sites Summary (Admin only)

On the Weekly tab, click ⬇ Download All-Sites Summary. Aggregates all active sites for the selected week into one presentation.

ℹ️ The all-sites exports will return an error if no sites have submitted data for the selected period. Remind site teams to submit before generating.

The 7-step monthly runbook

  1. Make sure the data is fresh. Open the Main Dashboard — if the data freshness chip in the top bar is green ("synced <4h ago"), you're good. If it's amber/red, click ⚡ Force Sync and wait for it to finish. Skip the Activity Tracker check if the period hasn't ended yet — tracker is monthly, you want the whole month closed.
  2. Open the Executive Report page (📊 Executive New Report or the direct URL above). At the top of the page:
    • Period dropdown → pick the month you're reporting on.
    • Site filter → leave on All Sites for the group deck (or pick a specific site if you're producing a per-site variant).
    • Group filter → leave at default (All Groups). Don't apply a group filter unless you specifically want a slice; the cover always reads "Operations Summary" regardless.
    Wait for the live KPI tiles + charts on the page to populate (~5-10s).
  3. Fill in the IT Governance commentary cards. Scroll down to Section 07 — IT Governance Narrative. Click ✏ Edit on each of the 4 cards and type bullet-style prose — one item per line:
    • ✅ Progress since last period — wins, milestones met, automation rolled out, recruitment closed
    • ⚠ Issues / Risks / Comment — incidents, blockers, vendor delays, capability gaps
    • 📅 Activities for next period — launches, rollouts, governance reviews
    • 🎯 Action items & priorities — format: [P1] Improve FRT SLA — Owner: Service Desk Manager (one per line, optional [P1]/[P2]/[P3] badges, optional — Owner: NAME suffix)
    These four fields ARE NOT auto-filled by AI — they're the only narrative sections you write yourself each month. Empty fields render a discreet placeholder on the slide rather than blank space.
  4. Click 🤖 Analyze & Save. The AI reads your data + governance prose and generates the analyst commentary for slides 4-9 (helpdesk, SLA & ageing, CSAT, change, major incidents). You'll see a progress panel: "Analysis in progress…" followed by ~5 status lines. Total time: ~30-45 seconds.
    ℹ️ The AI now reads the >60-day backlog ticket subjects to identify why tickets are blocked (vendor / procurement / infra / approval / user access) and includes the analysis at the bottom of slide 6's commentary band. For major incidents, it reads the RCA / Corrective Action / Lessons Learned UDFs to spot recurring root causes.
  5. Review the auto-filled commentary. Each section card now has analyst text. Read each one. Edit any sentence that's off — click ✏ Edit and type. The AI is conservative but occasionally surfaces something obvious that needs nuance (e.g. "consider FRT SLA target" when it's already on the action plan).
  6. Export the deck. Two buttons in the action bar at the bottom:
    • 📤 Export PPTX — client-side render in your browser. Faster (~5 sec). Produces the canonical 11-slide deck. Filename: IT_Operations_Report_<Month>_<Year>.pptx.
    • 📊 Executive New Report — server-side render. Slower (~30 sec, makes more AI calls). Includes the same 11 slides + ALSO appends the 2 Activity Tracker slides at positions 9 & 10 if the tracker has data for the period. Filename: Endeavour_Executive_Report_<Year>_<MonthName>.pptx.
    For a normal monthly deck, use Export PPTX. Use Executive New Report when you want richer AI commentary or are comfortable with a longer render.
  7. Open the file, scan it, distribute. Recommended sanity checks before sharing:
    • Cover shows the right month (e.g. "MARCH 2026" in big gold)
    • Slide 2 governance panels show your typed bullets (not the placeholder)
    • Slide 9 Incident Register dots are mostly grey (not red) — grey means PIR was not required; red means RCA / CA / LL is genuinely missing
    • Slides 10 & 11 (tracker) show the current month's % scores and site cards in the right colour
    • Footer page numbers read 2/11 through 11/11 (cover unnumbered)
    Save to your distribution folder and share via Teams / email.

Common gotchas

  • Slide 7 says "No survey data" — the survey nightly sync hasn't run for the period, OR there are genuinely no responses. Trigger POST /api/sync/trigger/survey from an admin shell to refresh.
  • Slides 10 & 11 are missing or wrong month — the tracker has no data for that month. Site IT leads need to enter their tracker actuals first (Activity Tracker → Input tab → save).
  • "403 Forbidden" when clicking Analyze & Save or Export — your account is missing the report-author role. Ask an admin to grant it from the Admin tab.
  • Major Incident commentary says "follow up" generically — the major-incident UDFs (Root Cause Analysis, Corrective Action, Lessons Learned) are empty in Zoho. Ask the incident owner to fill them, then trigger POST /api/admin/refresh-major-incident-udfs to backfill the DB.
💡 The 4 Governance cards (Progress / Issues / Activities / Actions) and the auto-filled analyst commentary are NOT persisted server-side — they live in your browser session. If you reload the page, they reset. Always run Analyze & Save + Export in the same session.

7Admin Panel

Accessible only to accounts with the admin role (or any role above it in the hierarchy) via the ⚙️ Admin tab in Site Reports.

  • User Management — create, edit, and deactivate user accounts; assign hierarchical and feature roles (see §2).
  • Site Management — add or deactivate sites; map each site to its Zoho group(s); set sort order for report generation. Add / Disable requires executive or higher; renaming an existing site is intentionally not exposed.
  • Department Management — manage the editable department list used by the action-items dropdown (Mining, Technical Service, Processing, etc.).
  • Week Management — view and manage the list of reporting weeks.
  • Report Oversight — view all submitted/draft reports across all sites; re-open a report if corrections are needed.

Editing a user — the role picker

Click Edit on any row in the Users table. The modal shows two role groups:

  • Hierarchical (radio — pick one): Super Admin · Executive · Admin · Editor · Viewer
  • Feature roles (checkboxes — pick any): tracker-admin · tracker-editor · report-author · audit-viewer

The user list table renders each user's roles as colour-coded chips: hierarchy tier in its standard role colour, and feature roles in a teal pill. If a user has multiple feature roles, they appear stacked.

💡 To grant a site IT lead local tracker access, assign them editor + tracker-editor and make sure their Site field is set — the tracker scope follows that field. For a lead who covers several sites, tick them under Extra sites (the list shows a "+N" badge).

Action items — Department + Comment

Each action item has a mandatory Department (dropdown — Mining, Technical Service, Processing, Maintenance, Supply Chain, Security, Finance, Human Resource, Social Performance, General Manager, or any custom department added in Department Management) and an optional Comment.

Bulk import via CSV is supported: prepare a file with English headers (Task, Department, Priority, Due Date, Owner, Status, Comment) and click Import CSV on the Actions tab. The importer is forgiving (case-insensitive headers, lenient validation) and shows row-level errors before committing — successful rows are appended in append-mode.

⚠️ Deactivating a site removes it from PPTX generation but does not delete its historical data. Disabled sites stay in the database for audit purposes; activate them again to bring them back into reports.

Asset reminders (super_admin)

Envois automatiques ▸ Rappels parc arms two e-mails, both OFF by default: a weekly recap per site (schedule on the card, Monday 07:00 suggested) and a same-day "new hardware" alert after the nightly assets sync. They go to the site's confirmed asset manager (set in Automated Reports ▸ Recipients), with the confirmed coordinator in copy; without a confirmed asset manager, to the confirmed coordinator alone. No amount is ever sent. Use Preview (optionally one site) before arming.

The weekly recap is deduped same-day only: clicking Send now on a later day for a week that was already mailed sends it again.

7.3 Active Sessions — Who's using the dashboard right now

The 🟢 Active Sessions card on the Admin page shows every user who has made an authenticated request in the last few minutes. Useful for answering "is anyone using this before I restart the server" or "did Aïssatou actually log in this morning."

  • Idle window — dropdown in the card header (1 min / 5 min / 15 min / 1 h / 24 h). Defaults to 5 min.
  • Auto-refresh — every 30 seconds while the Admin tab is active and the browser tab is visible. Manual 🔄 Refresh button also available.
  • Last activity — shows relative ("● now", "12 min ago", "1 h 30 min ago"); hover for the absolute timestamp.
  • Force Logout — super_admin only. Invalidates the session token immediately; the user sees "Not authenticated" on their next click and has to log in again. Disabled on your own row to prevent lockout.
ℹ️ Admins (non-super_admin) see the card as read-only — they can see who's online but cannot force-logout. Sessions automatically expire after 24 hours of no activity.

7.4 Risk Register — Site Code Mapping (super_admin only)

The Risk Register monthly Occurrence export aggregates incidents per site, but SDP / Zoho stores the site as a free-form text label (HOUNDE, Sabodala, MANA…) while the Risk Register expects short codes (HGO, SGO, MGO…). The 🛡 Risk Register — Site Code Mapping card on the Admin page lets a super_admin maintain this mapping without a code deploy.

  • + New Mapping — adds a SDP label → register code entry. The code dropdown lists the 10 canonical codes (IGO / SGO / MASSAWA / HGO / KGO / MGO / EXPLO / OUAGA OFF1 / EMSA / SML).
  • Unmapped sites for [month] — diagnostic strip showing SDP labels that appear in incidents this month with no current mapping. Click + Map on a chip to pre-fill the New Mapping modal.
  • Edit — change the code an existing label maps to. The label itself is locked (it's the primary key).
  • Delete — removes a mapping. Future tickets with that label will appear as unmapped again.

Changes take effect immediately on the next export — no page reload or server restart required.

7.7 Security: sign-in, audit, Microsoft groups (super_admin)

  • Sign-in throttling. After 10 failed passwords on one account within 15 minutes, that account is blocked for 15 minutes (even with the right password); 30 failures from one address block the address. The counters survive a server restart. Every block is a login_throttled event in System Logs.
  • Break-glass account. When Microsoft sign-in is required (mode only), only the break-glass user can still use a password; each of its sign-ins is a risk event (breakglass_login).
  • Audit journal. Every change made through the dashboard (create, update, delete) and every refused access (403) is recorded in System Logs, category api: who, which page/route, result. The content of the change is not stored. Entries are kept 12 months.
  • Roles and sites from Microsoft groups (Admin ▸ Microsoft SSO, off by default). When on, each Microsoft sign-in recomputes the person's roles and sites from the Entra groups listed in the map; someone in none of those groups can no longer sign in. super_admin is never granted by a group.
  • People who left (same card). preview lists, every night, the accounts whose Microsoft identity was deleted or disabled, without changing anything (result in Sync health, job entra.deprovision); on deactivates them and closes their sessions. A run that would deactivate more than 20 % of the accounts is refused.
  • Incidents: the procedure (who to call, which secrets to replace, how) is in docs/ops/INCIDENT-RESPONSE.md.

16.2 How the modules connect

  • Two identity hubs — sites and users — are the only cross-module links. site_module_codes maps one site to its per-module code (Ity is SMI in Meetings but ITY in the Tracker).
  • FK-linked internally — each module is a small tree: a meeting owns its issues, which own their actions; a report owns its KPIs, lights and action items.
  • Soft-linked by code — Helpdesk hot data and Assets carry free-text site / group columns matched in application code, never a database foreign key. This is why site-name spelling consistency matters.

16.3 Backup, rollback & cohabitation

  • One backup unit — a single pg_dump of sdp_dashboard captures everything (_sdp_admin → option 5).
  • Per-module rollback — each module has a *_BACKEND flag; unsetting it and restarting falls back to that module's frozen SQLite archive.
  • Cohabitation — sdp_dashboard is a peer of the 4MyPeople appliance database fmp_v2 on the same cluster; the appliance's destructive operations are scoped to fmp_* and never touch the SDP database.

17Installer & Maintenance

For the IT administrators of the server. SDP-Setup-<version>.exe unpacks the bundle and opens the Setup.bat console menu (elevated). The menu is built to prevent accidents: it reads the real state of the server first, recommends a mode, and asks for an exact typed phrase before anything destructive. The full operator guide is docs/INSTALLER.md.

17.1 Situation & menu

  • Situation block — before the menu, the installer reads the install folder, the installed and bundle versions, .env, pm2, the port, the database (size and row counts) and the last restore point. It reads them again after every completed action.
  • Grouped menu — RECOMMENDED first, then OTHER, DATA and MAINTENANCE. Options that cannot apply are labelled and refused: unknown state, older bundle (downgrade), nothing installed, incomplete install, no demo dataset.

17.2 Red confirmation screen

Every destructive action shows a red screen: what will happen, what is at stake (real database size and counts, version, last restore point) and what protects you. The action continues only if you type the exact phrase:

ActionPhrase to type

Drop and recreate the database (after Reinstall)DROP <database>
Fresh install over an existing installOVERWRITE <COMPUTERNAME>
Demo dataset over an existing installDEMO <COMPUTERNAME>
Restore a restore pointRESTORE <yyyymmdd>
⚠️ Anything else, or an empty answer, cancels with “nothing changed”. If the confirmation script is missing or crashes, the action is refused. The database drop question is only asked when the database is reachable.

17.3 Safety guarantees

  • Backup before any deletion — a restore point is taken before the database step; a drop is refused unless that restore point holds a complete dump of the same database.
  • Automatic rollback — if a step fails after the backup, the previous state is put back (exit code 2).
  • Data check — row counts are compared before and after; a drop in a count is shown in red with the restore point to use. It never triggers a rollback.
  • Run summary — the same eight lines on screen and in summary.txt: Mode, Version, Restore point, Database, .env, Data check, Log, Summary.
  • Secrets — passwords never appear on a command line or in a log.
  • Exit codes — 0 success, 1 failure, 2 rolled back, 3 completed with a warning (demo dataset not loaded) or restore refused before any change.

17.4 Restoring a restore point

Available from option 6 of Setup.bat and option 6 of _sdp_admin.cmd, both through the red screen. Before touching anything, the restore takes a pre-restore point of the current state (the two newest are kept), including a dump of the database it is about to replace. It refuses — with nothing changed — when that dump is incomplete, when .env or the zip cannot be read, or when the dump comes from a newer PostgreSQL than the server. If the import fails later, the message names the pre-restore point to restore.

18IT Assets (module)

Open Insights → Assets. One page, seven tabs, one shared filter bar (site, state, product type, manufacturer, search). The filter you set stays as you move between tabs, and the tab is in the URL — assets.html#hygiene re-opens where you left off.

The register is not live. Assets are re-synced from AssetExplorer every night at 04:30, and the effort snapshot is taken right after. A correction you make in AssetExplorer therefore appears here after the next sync, not the same minute. The line under the title states the last synchronisation; if it reads “Parc jamais synchronisé”, no import has ever landed and every count below is meaningless — tell IT.

18.1 Inventory

The list of assets, as SDP holds them: name, product, site, state, manufacturer, serial, RAM, free disk, last scan, user, department, and the money columns converted to USD (purchase, book value, TCO). Excel export respects the filter bar. Clicking a chart segment opens the matching rows with a CSV export.

18.2 Hygiene

How trustworthy the register is, as work lists you can clear:

  • Discovered — seen by a scan but never filed as an asset.
  • Never successfully scanned / Ghost — a ghost was healthy once and has not been seen for more than 90 days. The two never overlap.
  • No owner · no acquisition date · no cost — the completeness gaps. These three drive the per-site completeness percentage.
  • No QR code — the SDP field Barcode / QR code is empty. The asset manager generates it from the Service Tag, so a barcode equal to the serial is the NORMAL filled state, not an auto-fill. The Asset Tag is a different field and is not the QR code.
  • In repair / expired / lost — lifecycle exceptions to review.

Each tile drills into the rows and exports to Excel. No amount is ever shown on this tab.

18.3 Finance & Licences

Value of the fleet per site in USD (assets are held in XOF and converted with the rate set in Admin → Assets finance), the book value we compute ourselves from the depreciation policy, SDP's own book value as a cross-check, and the software licences: type families, expiry buckets, and the purchased-versus-installed compliance verdict that SDP itself publishes.

💡 A currency label is always written next to an amount. The $ in the AssetExplorer export is not reliable: hardware costs are XOF, licence costs are USD.
Amounts are restricted. This tab, the Investment tab and the money columns of the inventory (and its Excel export) require an admin account. Every other tab — Inventory, Hygiene, Hardware, Progress, Réconciliation — stays open to any signed-in user: a worklist without amounts is still a worklist.

18.4 Hardware

Health of the machines: RAM below 8 GB, system disk below 10 % free, refresh due (past the useful life for its product type) and no real monitor. Cameras, webcams and virtual monitors are filtered out of the monitor count, and the no-monitor list only covers workstation-type devices — a headless server is not a finding.

18.5 Progress — the effort score

The effort score is the mean of six good-state rates (cost · acquisition date · owner · scan · QR code · enrolment), from 0 to 100, snapshotted every night. The tab shows the per-site ranking, the change over roughly 30 days, the most improved site, and the six components for the site you click.

  • “Δ non comparable” means there is no snapshot old enough to compare against — it is not a score of zero.
  • The trend line breaks where a day has no snapshot; it is never drawn through a gap.
  • The ranking counts every site that has a snapshot, whatever its size, so a very small site can sit at the top. Read the score next to the fleet size.
  • A new site sees nothing until two snapshots exist — that is the “collecting data” state, not a failure.

18.6 Investment

Historical spend and a forward forecast: hardware replacement driven by the depreciation useful life, software renewal driven by licence expiry (subscriptions recur every year; there is no depreciation on software). Anything already past due lands in Due now; anything beyond the horizon is counted, not costed.

Read the coverage banner before the amounts. A hardware line only enters the forecast if it has an acquisition date AND a non-zero cost AND a lifecycle policy. On several sites that is true for none of the fleet, so the forecast can rest on a handful of assets. The banner states exactly how many, and why the others are excluded. When it reads “couverture inconnue”, the eligible count could not be computed at all — do not present the amount.

18.7 Réconciliation

Compares the register with what Active Directory, Entra and Defender see, and produces two lists: gaps (seen recently elsewhere, missing from SDP) grouped by OU — because a GPO is attached to an OU, not to a site — and retirement candidates (in SDP, seen nowhere for 90 days).

  • Retirement candidates are not applicable until at least one dated observation has been imported. The screen says so rather than listing the whole fleet.
  • Equipment that never joins a domain (switches, access points, firewalls, printers) is excluded from the retirement list — it would be a permanent false positive.
  • Candidates that look like a rename, an off-network machine or a never-scanned asset are set aside with their reason instead of being proposed for retirement.
  • A hostname carries the site where the machine was provisioned, not where it is today. For an asset SDP already knows, the site in SDP is the authority.
💡 Exporting the gaps in the SDP import format is not available: the import template was never supplied, and it will not be guessed.

19Teams SLA alerts

Technicians read Teams more than e-mail. Every 5 min the dashboard reads the open tickets straight from the ServiceDesk Plus API and posts one card per SDP group in that group's Teams channel, before the first-response and resolution SLA are breached. Major incidents follow their own process and are not part of these cards.

19.1 What is sent, and when

  • First response due soon — P1 10 min, P2 20 min, P3 60 min, P4 4 h before the deadline.
  • Resolution due soon — once 75 % of the resolution time is used.
  • SLA breached (first response or resolution) — announced only if the breach is less than 60 min old, so switching on never floods a channel with last week's breaches.
  • Unassigned — a ticket with no technician after 30 min (tickets less than 24 h old).

Each ticket is announced once per kind of alert, never twice. Tickets whose SLA is paused in SDP (On Hold, Awaiting Reply, Approval pending, PO Raised, Pending Verification) and finished tickets never alert. Tickets created more than 30 days ago are ignored (adjustable). Each line of the card links to the ticket in SDP.

19.2 Create the channel webhook (Teams)

  1. In Teams, open the channel (e.g. Abidjan IT Support Notification), click ⋯ next to its name → Workflows.
  2. In Find templates, type webhook and choose Send webhook alerts to a channel (older name: Post to a channel when a webhook request is received).
  3. Give it a name (e.g. SLA alerts — Abidjan), click Next, check that the team and the channel are the right ones, then Add workflow.
  4. Teams shows a URL: copy it and click Done. You can find it again later in Workflows → the workflow → the "When a Teams webhook request is received" step.
The webhook URL is a secret. Anyone who has it can post in the channel. Paste it only into the dashboard — not in an e-mail, a chat or a ticket. The workflow runs under the account that created it: if that account is disabled, the cards stop — create it with a service or team-lead account.

19.3 Connect it in the dashboard

  1. Open Admin → 🔌 Intégration API → Alertes SLA (super_admin).
  2. Under 2 · Canaux Teams par groupe, click + Ajouter un groupe.
  3. Groupe SDP: pick the exact SDP group name from the suggestions (e.g. Abidjan IT Agents). The name must match SDP; upper/lower case does not matter. The group * is the default channel for every group that is not listed.
  4. URL du webhook: paste the URL copied in Teams, then click Enregistrer. The URL is never shown again — the row only says ✓ enregistrée.
  5. Click Tester on that row: a TEST card must appear in the channel within a few seconds.
  6. Click Aperçu (sans envoi): the group must appear with its channel, and you see which tickets would be announced right now. Nothing is posted.
  7. If Armer les alertes is already ticked (the alerts are live for other groups), the new channel receives cards from the next 5-minute pass. Otherwise tick it and save.
💡 To change a channel's URL, type the new one in the row and save; leaving the field empty keeps the stored URL. To stop a channel, remove its row (✕) and save.

19.4 Phone notifications & troubleshooting

  • No sound on the phone? A card posted in a channel only alerts people who asked for it. Each technician: channel ⋯ → Channel notifications → Custom → All new posts: Show in Activity and banner. This is a personal setting; the dashboard cannot set it for them.
  • Tester works but no real card arrives — there may simply be no ticket close to its SLA for that group: check with Aperçu. If the group does not appear in the preview, its name does not match SDP.
  • The group appears without a channel in the preview — no row matches its name and there is no * row.
  • Tester fails — the URL was not copied whole, or the workflow was deleted or turned off in Teams: recreate it and save the new URL.
  • The line Dernier passage at the top of the card shows when the last 5-minute pass ran.

Cliquez sur 📋 Site Reports dans l'en-tête pour accéder au module de reporting hebdomadaire. Chaque équipe IT de site soumet un rapport par semaine couvrant les KPIs infrastructure, les métriques helpdesk, les points saillants et les actions à suivre. Le PPTX mensuel est construit automatiquement à partir de ces soumissions hebdomadaires.

4.1 KPIs Infrastructure

Renseignez la Section 1 — Infrastructure KPIs avec les valeurs réelles de cette semaine pour chaque système surveillé (disponibilité WAN, serveurs, taux de succès des sauvegardes, etc.).

  • Cliquez sur 📋 Copier depuis la semaine précédente pour pré-remplir toutes les lignes depuis le rapport de la semaine dernière. Le nom du service, le nom du KPI, la Cible et le Statut/Tendance précédents sont reportés — la colonne Valeur actuelle est intentionnellement effacée pour que vous ne saisissiez que les chiffres de cette semaine. La valeur de la semaine précédente est conservée en mémoire pour calculer automatiquement la Tendance.
  • Dès que vous saisissez une valeur numérique, le Statut (🟢/🟡/🔴) est défini automatiquement en comparant la valeur à la Cible, et la Tendance (▲/→/▼) est définie en comparant la valeur à celle de la semaine précédente — aucune sélection manuelle nécessaire.
  • Pour les entrées non numériques (ex. « N/A », « OK », texte libre), le calcul automatique ne s'applique pas. Définissez manuellement le Statut et la Tendance pour ces lignes.
⚠️ Les valeurs de Statut / Tendance saisies manuellement sont remplacées au moment de la génération PPTX pour les lignes numériques. Même si vous avez défini manuellement une Tendance dans le formulaire et sauvegardé le rapport, le générateur PPTX recalculera la Tendance à partir des valeurs réelles (semaine actuelle vs semaine précédente). La diapositive affichera la direction calculée — pas ce que vous avez saisi. Pour les lignes non numériques sans valeur précédente à comparer, la valeur manuelle sauvegardée est conservée.
💡 Copier depuis la semaine précédente est le point de départ recommandé chaque semaine — c'est un gain de temps considérable pour les sites avec de longues listes de KPIs.

Cliquez sur ⚡ Fill from OPManager / Meraki pour auto-remplir les cellules Valeur actuelle vides depuis la supervision de cette semaine (WAN1/WAN2 depuis Meraki, LAN/WLAN/Serveurs depuis OPManager). Cela n'écrase jamais une valeur que vous avez saisie. Survolez un chiffre auto-rempli pour lire comment il a été mesuré.

💡 La disponibilité WAN est « event-based ». Les chiffres WAN1/WAN2 viennent du journal des coupures — le statut de l'uplink relevé par Meraki toutes les 5 minutes, agrégé sur la semaine du rapport — et non de la perte de paquets (un lien totalement coupé rapporte 0 % de perte : la perte ne peut donc pas mesurer la disponibilité). C'est notre mesure OPS, cohérente avec le dashboard WAN Health. Comme le fait Meraki, les pannes du boîtier entier / coupures de courant (boîtier hors-ligne) sont exclues du dénominateur — seules les coupures du lien par ISP réduisent le chiffre. Ce n'est pas le « % Time Up » officiel du rapport Meraki, que Meraki n'expose par aucune API. Si le collecteur WAN n'a pas encore tourné, les cellules WAN restent vides plutôt que d'afficher un chiffre fabriqué — saisissez la valeur manuellement ou attendez le collecteur.

4.2 Métriques Helpdesk

La Section 2 — Helpdesk Metrics est pré-remplie avec les données Zoho du groupe de votre site. Vérifiez les chiffres, apportez les ajustements manuels si nécessaire, et sauvegardez.

Le panneau Tech Break Pool permet aux coordinateurs d'indiquer quels techniciens sont en pause. Cliquez sur une pastille pour l'ajouter ; cliquez à nouveau pour la retirer.

4.3 Points saillants (Low / High Lights)

Saisissez uniquement les incidents et réussites survenus cette semaine spécifique. Ne copiez pas les éléments de la semaine précédente — le système collecte toutes les semaines automatiquement et le rapport mensuel inclura les entrées de chaque semaine.

  • ▼ Incidents & Problèmes : pannes, perturbations ou dégradations de service survenus cette semaine.
  • ▲ Réussites & Réalisations : achèvements, améliorations ou résultats positifs de cette semaine.
  • Changements en cours / En attente : demandes de changement actives ou à venir. Saisissez un changement une seule fois au début — ne le ressaisissez pas chaque semaine.
⚠️ Si vous répétez le même élément chaque semaine, il n'apparaîtra qu'une seule fois dans le PPTX mensuel (dédupliqué automatiquement), associé à la première semaine où il a été saisi. Saisissez chaque élément une seule fois.

4.4 Actions à suivre

Listez les tâches nécessitant un suivi cette semaine. Ne retapez pas une action déjà suivie — reconduisez-la et mettez à jour son Statut (ouvert → en cours → clôturé).

  • Reconduction automatique — à l'ouverture d'une semaine vierge, les actions non résolues de la semaine précédente sont pré-remplies en brouillon (bandeau « ↩ N action(s) reconduite(s) »). Vérifiez responsable, échéance et statut, puis Enregistrez ; Annuler la reconduction les retire.
  • ↵ Import open actions from a previous week — choisissez une semaine, puis cochez les actions à reprendre. Une action non importable est grisée avec la raison : déjà dans ce rapport (enregistrée ou juste tapée), fermée depuis en Wxx, annulée ou fermée. La liste des semaines ne compte que les actions réellement importables.
  • Code de groupe — chaque action porte un badge coloré #CODE et « suivie depuis Wxx · N sem. ». Toutes les semaines d'une même action ont le même code ; deux actions au titre proche mais au code différent sont deux actions différentes. Survolez la cellule de la tâche pour voir le code.
  • ⚯ Fusionner des doublons — cochez deux actions ou plus du site (toutes semaines) qui sont en fait la même : la plus récente l'emporte, les autres prennent son code de groupe et son libellé. Tout le groupe est déplacé (chaque semaine plus ancienne aussi), une vieille copie ne peut donc plus revenir comme ouverte. Les doublons déjà existants ne fusionnent pas tout seuls — fusionnez-les une fois.
  • Annuler une action demande une justification (la même fenêtre que pour les statuts des réunions) ; elle est ajoutée au Comment de l'action sous la forme « Cancelled: … ». Changé d'avis ? Remettez le statut précédent — ou passez par le hub Site Actions (12.9).
ℹ️ Le PPTX mensuel affiche chaque action une seule fois, avec son statut le plus récent sur l'ensemble des semaines soumises. Si la même tâche apparaît en semaine 1 comme « ouverte » et en semaine 4 comme « clôturée », le PPTX l'affichera comme clôturée. Les doublons entre semaines sont automatiquement supprimés.
⚠️ Ne créez pas une nouvelle action pour quelque chose qui existe déjà — même si elle est toujours ouverte. Utilisez Importer les tâches ouvertes de la semaine précédente pour la reporter, puis mettez à jour le statut. Créer des doublons entraînera l'apparition de la même tâche deux fois dans le rapport mensuel.

4.5 Soumettre un rapport

  1. Complétez les quatre sections (Infrastructure, Helpdesk, Points saillants, Actions).
  2. Vérifiez le résumé en haut de la page.
  3. Cliquez sur le bouton vert ✅ Submit Report.
  4. Une bannière de confirmation indique que le rapport est soumis. Le statut passe à Submitted.
⚠️ Une fois soumis, un rapport ne peut être réouvert que par un Admin. Assurez-vous que toutes les informations sont correctes avant de soumettre.

4.6 Parc informatique (suivi des actifs)

L'onglet 5 · Parc informatique affiche quatre compteurs pour votre site, calculés sur la semaine du rapport : le matériel sans QR code (champ « Barcode / QR code » vide — tout le parc, pas seulement les arrivées de la semaine), sans date d'acquisition, sans coût d'achat et non assigné à un utilisateur (les quatre pour les états En service / En stock / En réparation). L'alerte du jour signale toujours le nouveau matériel sans QR code. Chaque compteur montre l'écart avec le rapport de la semaine précédente. L'onglet n'affiche que les compteurs — les listes détaillées sont envoyées au responsable parc du site dans les e-mails de rappel.

Deux notes facultatives : Traité cette semaine et Plan / blocages, enregistrées automatiquement. Les compteurs sont figés à la soumission et apparaissent dans l'e-mail hebdomadaire avec vos notes ; une note vide apparaît sous forme d'une pastille ambre « non renseigné ». Dans cet e-mail, le bloc Parc informatique (bandeau violet) ne montre que des compteurs, sans lien vers Assets. La soumission n'est jamais refusée, un avertissement s'affiche seulement.

ℹ️ Un site sans matériel dans l'inventaire (ex. Exploration, Tanda) affiche « Aucun matériel rattaché à ce site » et l'onglet compte comme terminé. Le statut automatique fonctionne désormais : quand les cinq onglets sont terminés le rapport passe Prêt — il faut toujours cliquer sur Soumettre.

La procédure mensuelle en 7 étapes

  1. Vérifiez la fraîcheur des données. Ouvrez le Tableau de bord principal — si la pastille de fraîcheur en haut est verte ("synchronisé <4h"), vous êtes bon. Si elle est orange/rouge, cliquez ⚡ Force Sync et attendez. Vérifiez aussi que le mois est terminé pour le tracker (cadence mensuelle).
  2. Ouvrez la page de Rapport Exécutif (📊 Executive New Report ou l'URL ci-dessus). En haut de page :
    • Menu Period → choisissez le mois à reporter.
    • Filtre Site → laissez sur All Sites pour le deck du groupe (ou choisissez un site spécifique pour une variante).
    • Filtre Group → laissez par défaut (All Groups). N'appliquez pas de filtre groupe sauf usage spécifique ; la couverture indique toujours "Operations Summary".
    Attendez que les tuiles KPI + graphiques live se peuplent (~5-10s).
  3. Remplissez les cartes de commentaire IT Governance. Descendez jusqu'à Section 07 — IT Governance Narrative. Cliquez ✏ Edit sur chacune des 4 cartes et tapez en style bullet — un élément par ligne :
    • ✅ Progress since last period — succès, jalons atteints, automatisations lancées, recrutements clos
    • ⚠ Issues / Risks / Comment — incidents, blocages, retards fournisseurs, lacunes de capacité
    • 📅 Activities for next period — lancements, déploiements, revues de gouvernance
    • 🎯 Action items & priorities — format : [P1] Improve FRT SLA — Owner: Service Desk Manager (un par ligne, badges [P1]/[P2]/[P3] optionnels, suffixe — Owner: NOM optionnel)
    Ces 4 champs ne sont PAS auto-remplis par l'IA — ce sont les seules sections narratives que vous écrivez chaque mois. Un champ vide affiche un placeholder discret sur la diapo plutôt qu'un blanc.
  4. Cliquez 🤖 Analyze & Save. L'IA lit vos données + votre prose de gouvernance et génère les commentaires d'analyse pour les diapos 4-9 (helpdesk, SLA & ageing, CSAT, change, incidents). Vous voyez un panneau de progression : "Analysis in progress…" suivi de ~5 lignes de statut. Durée totale : ~30-45 secondes.
    ℹ️ L'IA lit désormais les sujets des tickets >60 jours pour identifier pourquoi les tickets sont bloqués (fournisseur / approvisionnement / infra / approbation / accès utilisateur) et inclut l'analyse en bas du bandeau de commentaire de la diapo 6. Pour les incidents majeurs, elle lit les UDF Root Cause / Corrective Action / Lessons Learned pour repérer les causes racines récurrentes.
  5. Relisez les commentaires auto-remplis. Chaque carte de section a maintenant du texte d'analyse. Lisez chacune. Modifiez toute phrase qui sonne faux — cliquez ✏ Edit et tapez. L'IA est conservatrice mais surfacie parfois quelque chose d'évident qui mériterait nuance (ex : "envisager la cible FRT SLA" alors qu'elle est déjà au plan d'action).
  6. Exportez le deck. Deux boutons dans la barre d'action en bas :
    • 📤 Export PPTX — rendu côté navigateur. Plus rapide (~5 sec). Produit le deck canonique de 11 diapos. Nom : IT_Operations_Report_<Mois>_<Année>.pptx.
    • 📊 Executive New Report — rendu côté serveur. Plus lent (~30 sec, plus d'appels IA). Inclut les 11 mêmes diapos + AJOUTE les 2 diapos du Suivi des Activités en positions 9 & 10 si le tracker a des données pour la période. Nom : Endeavour_Executive_Report_<Année>_<NomMois>.pptx.
    Pour un deck mensuel normal, utilisez Export PPTX. Utilisez Executive New Report si vous voulez un commentaire IA plus riche ou si vous acceptez un rendu plus long.
  7. Ouvrez le fichier, parcourez-le, distribuez. Vérifications recommandées avant partage :
    • La couverture affiche le bon mois (ex : "MARCH 2026" en gros doré)
    • La diapo 2 montre vos bullets saisis (pas le placeholder)
    • Les pastilles de l'Incident Register diapo 9 sont majoritairement grises (pas rouges) — gris = PIR non requis ; rouge = RCA / CA / LL réellement manquant
    • Les diapos 10 & 11 (tracker) montrent les % du mois courant et les cartes site dans la bonne couleur
    • Les pieds de page indiquent 2/11 à 11/11 (couverture sans numéro)
    Sauvegardez dans votre dossier de distribution et partagez via Teams / email.

Pièges fréquents

  • La diapo 7 indique "No survey data" — la synchro nocturne des sondages n'a pas tourné, OU il n'y a vraiment aucune réponse. Déclenchez POST /api/sync/trigger/survey depuis un shell admin pour rafraîchir.
  • Les diapos 10 & 11 manquent ou affichent le mauvais mois — le tracker n'a pas de données pour ce mois. Les responsables IT site doivent saisir leurs réalisations tracker d'abord (Suivi des Activités → onglet Input → save).
  • "403 Forbidden" au clic sur Analyze & Save ou Export — votre compte n'a pas le rôle report-author. Demandez à un admin de l'attribuer depuis l'onglet Admin.
  • Le commentaire des incidents majeurs dit "follow up" génériquement — les UDF Zoho (Root Cause Analysis, Corrective Action, Lessons Learned) sont vides. Demandez au propriétaire de l'incident de les remplir, puis déclenchez POST /api/admin/refresh-major-incident-udfs pour backfiller la base.
💡 Les 4 cartes Governance (Progress / Issues / Activities / Actions) et les commentaires d'analyse auto-remplis NE sont PAS persistés côté serveur — ils vivent dans votre session navigateur. Si vous rechargez la page, ils sont réinitialisés. Lancez toujours Analyze & Save + Export dans la même session.

7Panneau d'administration

Accessible uniquement aux comptes ayant le rôle admin (ou tout rôle supérieur dans la hiérarchie) via l'onglet ⚙️ Admin dans les Rapports de site.

  • Gestion des utilisateurs — créer, modifier et désactiver des comptes ; attribuer rôles hiérarchiques et fonctionnels (voir §2).
  • Gestion des sites — ajouter ou désactiver des sites ; mapper chaque site à son/ses groupe(s) Zoho ; définir l'ordre de tri. Ajouter / Désactiver nécessite executive ou plus ; renommer un site existant n'est volontairement pas exposé.
  • Gestion des départements — gérer la liste éditable des départements utilisée par le menu déroulant des action items (Mining, Technical Service, Processing, etc.).
  • Gestion des semaines — consulter et gérer la liste des semaines de reporting.
  • Supervision des rapports — consulter tous les rapports soumis/brouillons de tous les sites ; rouvrir un rapport si des corrections sont nécessaires.

Édition d'un utilisateur — le sélecteur de rôles

Cliquez sur Edit sur n'importe quelle ligne de la table des utilisateurs. La fenêtre modale présente deux groupes de rôles :

  • Hiérarchique (radio — choisir un) : Super Admin · Executive · Admin · Editor · Viewer
  • Rôles fonctionnels (cases à cocher — toute combinaison) : tracker-admin · tracker-editor · report-author · audit-viewer

La table de la liste des utilisateurs affiche les rôles de chaque utilisateur sous forme de pastilles colorées : niveau hiérarchique dans sa couleur standard, et rôles fonctionnels en pastille teal. Si un utilisateur cumule plusieurs rôles fonctionnels, ils apparaissent côte-à-côte.

💡 Pour donner à un responsable IT site un accès local au tracker, attribuez-lui editor + tracker-editor et assurez-vous que son champ Site est renseigné — la portée du tracker suit ce champ. Pour un responsable qui couvre plusieurs sites, cochez-les dans Sites supplémentaires (la liste affiche un badge « +N »).

Action items — Département + Commentaire

Chaque action item a un Département obligatoire (menu déroulant — Mining, Technical Service, Processing, Maintenance, Supply Chain, Security, Finance, Human Resource, Social Performance, General Manager, ou tout département personnalisé ajouté dans la Gestion des départements) et un Commentaire optionnel.

L'import CSV en masse est supporté : préparez un fichier avec en-têtes en anglais (Task, Department, Priority, Due Date, Owner, Status, Comment) et cliquez sur Import CSV dans l'onglet Actions. L'importateur est tolérant (en-têtes insensibles à la casse, validation indulgente) et affiche les erreurs ligne par ligne avant l'engagement — les lignes valides sont ajoutées en mode append.

⚠️ Désactiver un site le supprime de la génération PPTX mais ne supprime pas ses données historiques. Les sites désactivés restent en base pour audit ; réactivez-les pour les ramener dans les rapports.

Rappels parc informatique (super_admin)

Envois automatiques ▸ Rappels parc arme deux e-mails, désarmés par défaut : un récap hebdomadaire par site (planification sur la carte, lundi 07:00 conseillé) et une alerte « nouveau matériel » le jour même, après la synchronisation nocturne. Ils partent au responsable parc confirmé du site (Automated Reports ▸ Recipients), coordinateur confirmé en copie ; sans responsable parc confirmé, au coordinateur confirmé seul. Aucun montant n'est envoyé. Faites un Preview (éventuellement sur un seul site) avant d'armer.

Le récap hebdomadaire n'est dédupliqué que le jour même : cliquer sur Envoyer maintenant un autre jour pour une semaine déjà envoyée la renvoie.

7.3 Sessions actives — Qui utilise le tableau de bord en ce moment

La carte 🟢 Active Sessions sur la page Admin affiche tous les utilisateurs ayant effectué une requête authentifiée dans les dernières minutes. Utile pour répondre à "est-ce que quelqu'un utilise ça avant que je redémarre le serveur" ou "Aïssatou s'est-elle effectivement connectée ce matin".

  • Fenêtre d'inactivité — menu déroulant dans l'en-tête de la carte (1 min / 5 min / 15 min / 1 h / 24 h). Défaut : 5 min.
  • Auto-rafraîchissement — toutes les 30 secondes tant que l'onglet Admin est actif et que l'onglet navigateur est visible. Bouton 🔄 Refresh manuel également disponible.
  • Dernière activité — affichage relatif ("● now", "12 min ago", "1 h 30 min ago") ; survolez pour le timestamp absolu.
  • Force Logout — super_admin uniquement. Invalide immédiatement le token de session ; l'utilisateur voit "Not authenticated" au prochain clic et doit se reconnecter. Désactivé sur votre propre ligne pour éviter le verrouillage.
ℹ️ Les admins (non-super_admin) voient la carte en lecture seule — ils voient qui est connecté mais ne peuvent pas forcer la déconnexion. Les sessions expirent automatiquement après 24 heures sans activité.

7.4 Registre des Risques — Mappage des codes site (super_admin uniquement)

L'export mensuel d'Occurrences du Registre des Risques agrège les incidents par site, mais SDP / Zoho stocke le site comme un libellé texte libre (HOUNDE, Sabodala, MANA…) tandis que le Registre attend des codes courts (HGO, SGO, MGO…). La carte 🛡 Risk Register — Site Code Mapping sur la page Admin permet à un super_admin de maintenir cette correspondance sans redéploiement de code.

16Architecture & Base de données

Référence technique pour les administrateurs et l'IT. Depuis août 2026, après l'achèvement de la migration SQLite → PostgreSQL (Assets fut le dernier module, basculé le 6 août 2026), les six modules opérationnels partagent une seule base PostgreSQL 17 nommée sdp_dashboard, hébergée sur le cluster géré par 4MyPeople. Ce n'est pas une base par application — c'est une seule base avec un préfixe de table par module.

16.2 Comment les modules se relient

  • Deux hubs d'identité — sites et users — sont les seuls liens inter-modules. site_module_codes mappe un site vers son code par module (Ity est SMI dans Réunions mais ITY dans le Suivi).
  • Liés par FK en interne — chaque module est un petit arbre : une réunion possède ses issues, qui possèdent leurs actions ; un rapport possède ses KPIs, lights et actions.
  • Liés par code (sans FK) — le hot data Helpdesk et les Assets portent des colonnes site / groupe en texte libre, rapprochées dans le code applicatif, jamais par une clé étrangère. D'où l'importance de l'orthographe cohérente des noms de site.

16.3 Sauvegarde, retour arrière & cohabitation

  • Une seule unité de sauvegarde — un pg_dump de sdp_dashboard capture tout (_sdp_admin → option 5).
  • Retour arrière par module — chaque module a un flag *_BACKEND ; le retirer et redémarrer revient à l'archive SQLite gelée de ce module.
  • Cohabitation — sdp_dashboard est un pair de la base fmp_v2 de l'appliance 4MyPeople sur le même cluster ; les opérations destructrices de l'appliance sont limitées à fmp_* et ne touchent jamais la base SDP.

17Installeur & maintenance

Pour les administrateurs IT du serveur. SDP-Setup-<version>.exe décompresse le paquet et ouvre le menu console Setup.bat (en administrateur). Le menu est conçu pour éviter les accidents : il lit d'abord l'état réel du serveur, recommande un mode et exige une phrase exacte avant toute action destructive. Le guide opérateur complet est docs/INSTALLER.md.

17.1 Situation & menu

  • Bloc situation — avant le menu, l'installeur lit le dossier d'installation, les versions installée et du paquet, le .env, pm2, le port, la base (taille et comptages) et le dernier point de restauration. Il les relit après chaque action terminée.
  • Menu groupé — RECOMMANDÉ d'abord, puis AUTRES, DONNÉES et MAINTENANCE. Les options impossibles sont libellées et refusées : état inconnu, paquet plus ancien (retour à une version antérieure), rien d'installé, installation incomplète, pas de jeu de démo.

17.2 Écran rouge de confirmation

Toute action destructive affiche un écran rouge : ce qui va se passer, ce qui est en jeu (taille et comptages réels de la base, version, dernier point de restauration) et ce qui vous protège. L'action ne continue que si vous tapez la phrase exacte :

ActionPhrase à taper
RéinstallationREINSTALL
Supprimer et recréer la base (après la réinstallation)DROP <base>
Installation neuve sur une installation existanteOVERWRITE <NOM_DE_LA_MACHINE>
Jeu de démo sur une installation existanteDEMO <NOM_DE_LA_MACHINE>
Restaurer un point de restaurationRESTORE <aaaammjj>
⚠️ Toute autre saisie, ou une réponse vide, annule avec « nothing changed ». Si le script de confirmation manque ou plante, l'action est refusée. La question de suppression de la base n'est posée que si la base est joignable.

17.3 Garanties de sécurité

  • Sauvegarde avant toute suppression — un point de restauration est pris avant l'étape base ; la suppression est refusée si ce point ne contient pas une copie complète de la même base.
  • Retour arrière automatique — si une étape échoue après la sauvegarde, l'état précédent est remis en place (code de sortie 2).
  • Contrôle des données — les comptages sont comparés avant et après ; une baisse s'affiche en rouge avec le point de restauration à utiliser. Ce contrôle ne déclenche jamais de retour arrière.
  • Résumé du run — les mêmes huit lignes à l'écran et dans summary.txt : Mode, Version, Restore point, Database, .env, Data check, Log, Summary.
  • Secrets — les mots de passe n'apparaissent jamais sur une ligne de commande ni dans un journal.
  • Codes de sortie — 0 succès, 1 échec, 2 retour arrière effectué, 3 terminé avec avertissement (jeu de démo non chargé) ou restauration refusée avant tout changement.

17.4 Restaurer un point de restauration

Disponible via l'option 6 de Setup.bat et l'option 6 de _sdp_admin.cmd, toutes deux avec l'écran rouge. Avant de toucher quoi que ce soit, la restauration prend un point pre-restore de l'état actuel (les deux plus récents sont gardés), avec une copie de la base qu'elle va remplacer. Elle refuse — sans rien changer — si cette copie est incomplète, si le .env ou le zip est illisible, ou si la copie vient d'un PostgreSQL plus récent que le serveur. Si l'import échoue ensuite, le message indique le point pre-restore à restaurer.

À lancer dans un PowerShell administrateur avant d'appliquer en production un paquet de déploiement qui transporte les outils d'installation. Il ne touche que C:\Apps\SDP-Dashboard-TEST (port 3457, pm2 sdp-test, base sdp_dashboard_test, points de restauration dans C:\Apps\SDP-Backups-TEST).

18Parc informatique (module Assets)

Ouvrez Insights → Assets. Une page, sept onglets, une barre de filtres commune (site, état, type de produit, fabricant, recherche). Le filtre choisi est conservé quand vous changez d'onglet, et l'onglet est dans l'adresse : assets.html#hygiene rouvre là où vous étiez.

Le registre n'est pas en temps réel. Les actifs sont resynchronisés depuis AssetExplorer chaque nuit à 04:30, et l'instantané d'effort est pris juste après. Une correction faite dans AssetExplorer apparaît donc ici après la synchronisation suivante, pas dans la minute. La ligne sous le titre indique la dernière synchronisation ; si elle affiche « Parc jamais synchronisé », aucun import n'a jamais eu lieu et tous les compteurs ci-dessous sont sans valeur — prévenez l'IT.

18.1 Inventaire

La liste des actifs tels que SDP les détient : nom, produit, site, état, fabricant, numéro de série, RAM, espace disque libre, dernier scan, utilisateur, département, et les colonnes financières converties en USD (achat, valeur comptable, coût total). L'export Excel respecte la barre de filtres. Un clic sur un segment de graphique ouvre les lignes correspondantes avec un export CSV.

18.2 Hygiène

La fiabilité du registre, sous forme de listes de travail à résorber :

  • Découvert — vu par un scan mais jamais enregistré comme actif.
  • Jamais scanné avec succès / Fantôme — un fantôme a été sain un jour et n'a plus été vu depuis plus de 90 jours. Les deux listes ne se recoupent jamais.
  • Sans utilisateur · sans date d'acquisition · sans coût — les manques de complétude. Ce sont ces trois-là qui déterminent le pourcentage de complétude par site.
  • Sans QR code — le champ SDP Barcode / QR code est vide. Le responsable parc le génère depuis le Service Tag : un barcode égal au numéro de série est donc l'état NORMAL rempli, pas un remplissage automatique. L'Asset Tag est un autre champ et n'est pas le QR code.
  • En réparation / expiré / perdu — les exceptions de cycle de vie à examiner.

Chaque tuile ouvre le détail et s'exporte en Excel. Aucun montant n'est affiché dans cet onglet.

18.3 Finance & licences

La valeur du parc par site en USD (les actifs sont tenus en XOF et convertis au taux réglé dans Admin → Assets finance), la valeur comptable que nous calculons nous-mêmes à partir de la politique d'amortissement, celle de SDP en contre-vérification, et les licences logicielles : familles de types, échéances, et le verdict de conformité acheté/installé publié par SDP lui-même.

💡 Un libellé de devise accompagne toujours un montant. Le $ de l'export AssetExplorer n'est pas fiable : les coûts matériels sont en XOF, les coûts de licence en USD.
Les montants sont réservés. Cet onglet, l'onglet Investissement et les colonnes financières de l'inventaire (ainsi que son export Excel) exigent un compte admin. Tous les autres onglets — Inventaire, Hygiène, Matériel, Progression, Réconciliation — restent ouverts à tout utilisateur connecté : une liste de travail sans montants reste une liste de travail.

18.4 Matériel

La santé des machines : RAM inférieure à 8 Go, disque système sous 10 % libre, renouvellement dû (durée de vie utile dépassée pour ce type de produit) et sans écran réel. Les caméras, webcams et écrans virtuels sont écartés du comptage, et la liste « sans écran » ne couvre que les postes de travail — un serveur sans écran n'est pas une anomalie.

18.5 Progression — le score d'effort

Le score d'effort est la moyenne de six taux de bon état (coût · date d'acquisition · utilisateur · scan · QR code · enrôlement), de 0 à 100, photographié chaque nuit. L'onglet montre le classement par site, l'évolution sur environ 30 jours, le site le plus en progrès, et les six composantes du site sur lequel vous cliquez.

  • « Δ non comparable » signifie qu'aucun instantané assez ancien n'existe pour comparer — ce n'est pas un score nul.
  • La courbe est interrompue là où un jour n'a pas d'instantané ; elle n'est jamais tracée à travers un trou.
  • Le classement retient tout site ayant un instantané, quelle que soit sa taille : un très petit site peut donc figurer en tête. Lisez le score à côté de la taille du parc.
  • Un site nouveau n'affiche rien tant qu'il n'a pas deux instantanés — c'est l'état « collecte en cours », pas une panne.

18.6 Investissement

La dépense historique et une prévision : remplacement du matériel piloté par la durée de vie utile de l'amortissement, renouvellement logiciel piloté par l'expiration des licences (les abonnements reviennent chaque année ; il n'y a pas d'amortissement sur le logiciel). Ce qui est déjà échu tombe dans À échéance maintenant ; ce qui dépasse l'horizon est compté, non chiffré.

Lisez le bandeau de couverture avant les montants. Une ligne matérielle n'entre dans la prévision que si elle a une date d'acquisition ET un coût non nul ET une politique de cycle de vie. Sur plusieurs sites, aucun actif ne remplit ces conditions : la prévision peut donc reposer sur une poignée de machines. Le bandeau dit exactement combien, et pourquoi les autres sont exclues. S'il indique « couverture inconnue », le nombre d'éligibles n'a pas pu être calculé du tout — ne présentez pas le montant.

18.7 Réconciliation

Compare le registre à ce que voient Active Directory, Entra et Defender, et produit deux listes : les écarts (vus récemment ailleurs, absents de SDP) groupés par OU — parce qu'une GPO se rattache à une OU, pas à un site — et les candidats au retrait (dans SDP, vus nulle part depuis 90 jours).

  • Les candidats au retrait sont non applicables tant qu'aucune observation datée n'a été importée. L'écran le dit au lieu de lister le parc entier.
  • Le matériel qui ne rejoint jamais un domaine (commutateurs, bornes Wi-Fi, pare-feux, imprimantes) est exclu de la liste de retrait : ce serait un faux positif permanent.
  • Les candidats qui ressemblent à un renommage, à une machine hors réseau ou à un actif jamais scanné sont écartés avec leur motif, au lieu d'être proposés au retrait.
  • Un nom de machine porte le site de provisionnement, pas le site actuel. Pour un actif déjà connu de SDP, c'est le site de SDP qui fait foi.
💡 L'export des écarts au format d'import SDP n'est pas disponible : le gabarit d'import n'a jamais été fourni, et il ne sera pas deviné.

19Alertes SLA dans Teams

Les techniciens lisent Teams plus que leurs e-mails. Toutes les 5 min, le dashboard lit les tickets ouverts directement dans l'API de ServiceDesk Plus et publie une carte par groupe SDP dans le canal Teams de ce groupe, avant le dépassement du SLA de première réponse puis de résolution. Les incidents majeurs suivent leur propre processus et ne sont pas concernés.

19.1 Ce qui est envoyé, et quand

  • 1re réponse bientôt due — P1 10 min, P2 20 min, P3 60 min, P4 4 h avant l'échéance.
  • Résolution bientôt due — dès que 75 % du délai de résolution est consommé.
  • SLA dépassé (1re réponse ou résolution) — annoncé seulement si le dépassement a moins de 60 min : l'activation ne noie jamais un canal sous les dépassements de la semaine passée.
  • Non assigné — un ticket sans technicien après 30 min (tickets de moins de 24 h).

Chaque ticket est annoncé une seule fois par type d'alerte. Les tickets dont le SLA est en pause dans SDP (On Hold, Awaiting Reply, Approval pending, PO Raised, Pending Verification) et les tickets terminés n'alertent jamais. Les tickets créés il y a plus de 30 jours sont ignorés (réglable). Chaque ligne de la carte renvoie au ticket dans SDP.

19.2 Créer le webhook du canal (Teams)

  1. Dans Teams, ouvrez le canal (ex. Abidjan IT Support Notification), cliquez sur ⋯ à côté de son nom → Workflows.
  2. Dans Find templates, tapez webhook et choisissez Send webhook alerts to a channel (« Envoyer des alertes webhook à un canal » ; ancien nom : Post to a channel when a webhook request is received).
  3. Donnez-lui un nom (ex. Alertes SLA — Abidjan), cliquez sur Next, vérifiez que l'équipe et le canal sont les bons, puis Add workflow.
  4. Teams affiche une URL : copiez-la puis cliquez sur Done. On la retrouve plus tard dans Workflows → le workflow → l'étape « When a Teams webhook request is received ».
L'URL du webhook est un secret. Quiconque la possède peut publier dans le canal. Collez-la uniquement dans le dashboard — jamais dans un e-mail, un chat ou un ticket. Le workflow tourne sous le compte qui l'a créé : si ce compte est désactivé, les cartes s'arrêtent — créez-le avec un compte de service ou de responsable d'équipe.

19.3 Le brancher dans le dashboard

  1. Ouvrez Admin → 🔌 Intégration API → Alertes SLA (super_admin).
  2. Sous 2 · Canaux Teams par groupe, cliquez sur + Ajouter un groupe.
  3. Groupe SDP : choisissez le nom exact du groupe SDP dans les suggestions (ex. Abidjan IT Agents). Le nom doit correspondre à SDP ; la casse n'a pas d'importance. Le groupe * est le canal par défaut de tous les groupes non listés.
  4. URL du webhook : collez l'URL copiée dans Teams, puis cliquez sur Enregistrer. L'URL n'est plus jamais affichée — la ligne indique seulement ✓ enregistrée.
  5. Cliquez sur Tester sur cette ligne : une carte TEST doit apparaître dans le canal en quelques secondes.
  6. Cliquez sur Aperçu (sans envoi) : le groupe doit apparaître avec son canal, et vous voyez les tickets qui seraient annoncés maintenant. Rien n'est publié.
  7. Si Armer les alertes est déjà coché (alertes actives pour d'autres groupes), le nouveau canal reçoit les cartes dès le prochain passage de 5 minutes. Sinon cochez-le et enregistrez.
💡 Pour changer l'URL d'un canal, saisissez la nouvelle dans la ligne et enregistrez ; un champ laissé vide conserve l'URL enregistrée. Pour arrêter un canal, supprimez sa ligne (✕) et enregistrez.

19.4 Notifications téléphone & dépannage

  • Pas de son sur le téléphone ? Une carte publiée dans un canal n'alerte que ceux qui l'ont demandé. Chaque technicien : canal ⋯ → Notifications du canal → Personnalisé → Tous les nouveaux billets : Afficher dans l'activité et la bannière (en anglais : Show in Activity and banner). C'est un réglage personnel ; le dashboard ne peut pas le faire à leur place.
  • Tester marche mais aucune vraie carte n'arrive — il n'y a peut-être simplement aucun ticket proche de son SLA pour ce groupe : vérifiez avec Aperçu. Si le groupe n'apparaît pas dans l'aperçu, son nom ne correspond pas à SDP.
  • Le groupe apparaît sans canal dans l'aperçu — aucune ligne ne porte son nom et il n'y a pas de ligne *.
  • Tester échoue — l'URL n'a pas été copiée en entier, ou le workflow a été supprimé ou désactivé dans Teams : recréez-le et enregistrez la nouvelle URL.
  • La ligne Dernier passage en haut de la carte indique l'heure du dernier passage de 5 minutes.
