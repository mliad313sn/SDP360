# Changelog

## 2.0.0-alpha.10 — 2026-10-19 — Étape 9 : studio de rapports IA, moteur d'engagement, publication externe
- Report Studio (`services/reportStore.js`, `services/reportGenerator.js`, `routes/reportStudio.js`, page `report-studio.html`): templates per audience (site / executive / council) on a published dashboard; a run resolves every figure through the dashboard viewer's own resolver (extracted to `services/dashboardData.js` — zero manual entry, zero figure deviation), writes a deterministic bilingual analysis (`services/reportAnalysis.js`), an optional AI commentary checked number by number against the canonical figures (`services/aiCommentary.js` — any foreign number → deterministic fallback; cloud providers receive anonymised data), and a frozen HTML pack; outputs HTML / PDF / CSV / PPTX / XLSX; draft → reviewed (note + rating 1–5) → published (refused before human review, frozen after); 3 templates seeded.
- Engagement (`services/engagementStore.js`, `services/alertEngine.js`, `services/engagementJobs.js`, `routes/engagement.js`, page `notifications.html`): alert rules (metric, scope, operator, threshold, streak, cool-down, channels, recipients; a null reading never fires), 12 rules seeded in-app only, evaluation every 15 min through the job runner + on demand, firings with false-positive tracking; in-app notification centre, comments, subscriptions with daily / weekly e-mail digests; signed expiring share links (hashed token, ≤ 90 days, max views, read receipts, revocation) and a public embeddable view with its own CSP.
- External publishing (`routes/extApi.js`, `services/odata.js`, page `integrations.html`): API consumers with hashed keys, scopes and daily quotas (429), call log; REST `/ext/v1/*` and OData v4 feed `/ext/odata/*` for Power BI (`$filter`, `$top`, `$skip`, `$orderby`, `$select`, `$count`); daily connectors (scheduled Excel by e-mail, webhook, SharePoint list via Microsoft Graph) armed by `publish_cron_enabled`, each self-skipping when unconfigured. Only site names leave the platform.
- PostgreSQL migration `reports/019`; config keys `engagement_*`, `publish_*`, `sharepoint_*`, `embed_frame_ancestors` (secrets write-only); nav Operations ▸ Report Studio / Notifications / Integrations; 6 optional jobs in the registry.
- Docs: dossier `docs/sdp360/design/ETAPE-09-rapports-engagement-publication.md`, help §26 EN/FR; tests `report-analysis` (5), `ai-commentary` (5), `alert-engine` (4), `odata` (3), `report-store` (2), `engagement-store` (5), `report-studio-routes.smoke` (4), `engagement-routes.smoke` (4), `pg-report-engagement-store` (1).

## 2.0.0-alpha.9 — 2026-10-19 — Étape 8 : cockpit de réunion, registre des décisions, portefeuille, demandes d'amélioration

- New feature role `committee-member`; pages `cockpit.html` (cadences, sessions, open decisions, full-screen live session), `portfolio.html` (tree, schedule alerts, risks, committee edit form, migration), `rfi.html` (submit, triage, score ordering); nav Operations ▸ Cockpit / Portfolio / RFI; dashboard seed `governance`.

## 2.0.0-alpha.8 — 2026-10-19 — Étape 7 : constructeur de trackers, saisie, liaisons aux sources, migration du tracker 2026
- Tracker definitions are persisted and versioned (`services/trackerStore.js`, sqlite on tracker.db + PostgreSQL via migration `tracker/002`): draft → published version N → retired, roll-back to any version; entries per unit × item × period with the closed-month lock (`public/lib/trackerMonthLock.js`) and unit scope for `tracker-editor`; per-unit targets merged into the engine.
- One scorer for everything: `services/trackerDefinitions.score` now aggregates like the inherited tracker (group-weighted mean over scored groups; a started COUNT without target scores 0) — the parallel run against `tracker-pptx` reads **≤ 0.1 pt** on the shipped 2026 programme (`services/trackerLegacy.js`, CSV report, `/api/trackers/legacy/compare`).
- Source bindings (`services/trackerSources.js`): an item carrying `source.metric` is filled from the KPI dictionary per unit × period (`POST /api/trackers/:key/sync`); a null reading is skipped, never written as 0.
- `routes/trackers.js` (list, catalogue, templates, definition CRUD, dry-run, publish/retire/versions/rollback, entries, targets, score, sync, xlsx import, Excel/PPTX exports, legacy compare/import/cut-over); pages `trackers.html` (entry grid + scores) and `tracker-builder.html`; nav Operations ▸ Trackers; 4 templates seeded as drafts (field dispatch, hardware deployment, site maintenance, meetings compliance); config key `tracker_engine_cutover`.
- Docs: dossier `docs/sdp360/design/ETAPE-07-trackers.md` (migration plan, arbitration points), help §24 EN/FR; tests `tracker-store`, `tracker-sources`, `trackers-routes.smoke`, `pg-tracker-store`.

## 2.0.0-alpha.2 — 2026-10-19 — Étape 1 : synchronisations fiables et observables
- One cron registry (`services/sync/jobs.js` + `schedule.js`): every scheduled job runs through the shared runner (overlap lock, exponential retry with Retry-After, run log, failure mirrored to `system_log`).
- Truncation guard before every Zoho reconciliation (`zoho-sync.js assertNotTruncated`): a partial export can no longer cascade into a mass delete.
- Alerts (`services/sync/alerts.js`): e-mail / Teams after 2 consecutive failures and when a job is older than its freshness window (once per 24 h). Config keys `sync_alert_enabled`, `sync_alert_recipients`, `sync_alert_teams_url` (secret), `sync_truncation_tolerance_pct`.
- `GET /api/sync/health` merges runner runs with legacy `sync_metadata` and labels each job ok / stale / error / never / idle.
- System Logs ▸ new "Sync health" tab.
- Meraki client keeps the HTTP status on errors so 429/5xx are retried.
