## 6. ITSM STANDARD DIVERGENCES (DASHBOARD-SIDE EDITORIAL CHOICES)

> **READ THIS BEFORE TOUCHING ANY KPI FORMULA.** The dashboard intentionally
> diverges from the AP canonical formulas in §1 for four metrics. The
> divergences align our KPIs with the ITSM industry standard (Actonic,
> Atlassian, Jira ITSM, ITIL convention), which is more discriminating
> when the open backlog dilutes the AP `/total` ratios. The divergences
> were debated and ratified 2026-06-02 — see git log around that date
> for the discussion thread.

### Why diverge from AP at all?

The AP canonical aggregates above use `count("RequestID")` (= ALL tickets,
open + closed) as the denominator for every percentage metric. This is
mathematically the most general formula but produces three problems
operationally:

1. **Inflated "in compliance" scores** — an open ticket whose SLA window
   hasn't elapsed yet is currently neither met nor violated; AP scores it
   as "within SLA" by default. With a heavy backlog, the SLA% reads green
   even when closed-ticket performance is amber.
2. **Diluted "problem" rates** — Reopen Rate and FRT-SLA % follow the same
   shape. An unresponded fresh ticket isn't a verdict on FRT performance,
   but AP counts it in the denominator anyway.
3. **Reopen Rate semantics** — an open ticket can't be reopened (semantically).
   Including it in the denominator suppresses the rate by ~30-40% on a
   typical SDP backlog.

The ITSM industry standard (Actonic "Closed vs. Reopened Report explained";
Atlassian Jira Service Management; ServiceNow Standard Performance Reports)
uses **verdict-only** denominators — only tickets where the metric's
verdict has been rendered (= closed, or = responded, depending on the
metric). That produces tighter, more discriminating signal.

### The 4 divergences

| # | Metric | AP canonical formula | Dashboard (ITSM) formula | Where applied |
|---|---|---|---|---|
| D1 | **Reopen Rate** | `reopened / count(RequestID)` (= `/total`) | `reopened-of-closed / closed-count` (= `/closed`) | `executive-report.html` `renderHelpdeskKpis()` + `buildAiSnapshot.helpdesk.reopenRate`; `executive.html` `_applyRawToKpiAndSla` reopen tile |
| D2 | **Resolution SLA %** | `countif(Overdue Status=0) / count(RequestID)` (= `met / total`) | `Requests within SLA - Closed Requests` / `Closed Requests Count` (= `met-of-closed / closed`) | All 3 places: KPI tile, AI snapshot, PPTX slide 3 |
| D3 | **First Response SLA %** | `sum(if FROS=true,1,0) / count(RequestID)` (= `violated / total`) | `violated-of-responded / responded` where `responded = count if Responded Time IS NOT NULL` | KPI tile + per-category/site sub-aggregates |
| D4 | **Change Success Rate** | `Completed / (Completed + Cancelled + Rejected)` (AP `All_Introduced_Change_Finalized_Count` denominator) | `successful / executed` where `executed = successful + failed + backed_out` (Cancelled / Rejected are EXCLUDED because they were never executed) | `_tallyChanges()` UDF-aware classifier already implements this — must replace the legacy inline regex in `renderChangeKpis()` |

### Why these 4 and not others?

| Metric | Verdict |
|---|---|
| % Escalated Requests | AP `/total` kept — escalation can happen on open OR closed tickets, no verdict gate. ✓ |
| % of SLA Violated (incident sense) | Same as D2 — divergent. The shape is identical to Resolution SLA %, just the inverse signal. |
| CSAT %, NPS | Already verdict-only (denominator = survey responders, not all tickets). ✓ |
| Survey Response Rate | Already verdict-only (denominator = closed-with-survey-sent). ✓ |
| FCR Rate | Already verdict-only (denominator = closed-and-responded). ✓ |
| Multi-Touch Rate | Custom CES proxy, no AP equivalent. ✓ |
| MTTR / Avg Resolution Time | AP raw fractional days `Time Elapsed in Hrs` — dashboard convention is `Math.floor` per ticket then mean. Editorial choice unrelated to ITSM denominator question; documented in CLAUDE.md commit 37c2b28 ruling. |

### Building blocks AP provides for the ITSM formulas

Good news: AP already exposes the closed-only counters as separate aggregate
columns, so the ITSM denominators don't require new SQL. The dashboard's
SQLite `request_records` table has all the raw fields (`request_pending_status`,
`overdue_status`, `responded_time`, `request_status`, `reopen_count`) so
the same logic ports verbatim.

```
AP column → SQLite equivalent → ITSM use
─────────────────────────────────────────
Closed Requests Count                  → request_pending_status = 0                 → ITSM denominator for D1, D2
Requests within SLA - Closed Requests  → pending_status=0 AND overdue_status=0      → ITSM numerator for D2
SLA Requests violated - Closed Requests → pending_status=0 AND overdue_status=1      → diagnostic counter
Reopen Requests Count                  → reopen_count > 0                           → ITSM numerator for D1 (filtered to closed)
First Response Overdue Status          → first_response_overdue IN (true,1,yes)    → ITSM numerator for D3 (filtered to responded)
Responded population                   → responded_time IS NOT NULL                  → ITSM denominator for D3
```

### ✅ BUGS FIXED — 2026-03-30 (v1.8.0)

#### FIX 1: `isResOverdue()` — Resolution SLA always reported 100%
**Root cause (dual bug):**
- `Due By Time` is empty for **all tickets** in this workspace → the primary timestamp path (`Resolved Time > Due By Time`) never executed
- The fallback check used `.toLowerCase() === 'yes'` but Zoho stores the value as `"1"` (numeric string) → never matched

**Fix applied in:** `public/index.html`, `public/executive.html`, `public/executive-report.html`, `server.js`
```js
// OLD (broken) fallback:
return (r['Overdue Status'] || '').toLowerCase() === 'yes';

// NEW (correct) — accepts all three Zoho formats:
const ov = (r['Overdue Status'] || '').toString().trim();
return ov === '1' || ov.toLowerCase() === 'yes' || ov.toLowerCase() === 'true';
```
The guard `if (!isRes) return false` was also relaxed — open overdue tickets now count as violations, matching Zoho AP formula #3/6 which uses `countif(Overdue Status = 1)` over **all** tickets (open + closed). Cancelled tickets remain excluded.

#### FIX 2: `First Response Overdue Status` — 1st Reply SLA always reported 100%
**Root cause:** The SQLite rebuild path in `server.js` (`_rebuildCacheFromSQLite`) mapped the field as `'First Response Overdue'` (missing " Status"). All browser code reads `r['First Response Overdue Status']` → field always undefined → 0 violations.

**Fix applied in:** `server.js` line ~2000
```js
// OLD (broken):
'First Response Overdue': r.first_response_overdue,

// NEW (correct):
'First Response Overdue Status': r.first_response_overdue,
```

#### FIX 3: `reports-db.js` SQL — first response overdue count missed `'1'` and `'Yes'`
**Fix applied in:** `reports-db.js` line ~1212
```js
// OLD: only matched literal 'true'
AND first_response_overdue='true'

// NEW: matches all three formats case-insensitively
AND (LOWER(first_response_overdue) IN ('true','1','yes'))
```

#### FIX 4: `executive.html` — `frViolated` missing `'yes'` variant
```js
// OLD: const frViolated = frOverdue === 'true' || frOverdue === '1';
// NEW: const frViolated = frOverdue === 'true' || frOverdue === '1' || frOverdue === 'yes';
```

- Our `EXPECTED_CHANGE_COLS` includes `Stage` but the Zoho API may return it differently

- This is both a formula column AND appears as a raw column in the Zoho API response (Zoho pre-computes it)

#### GAP 4: All-formula metrics are computed at query time
- **All aggregate formulas** (Open Requests Count, % within SLA, Change Success Rate, CAB Compliance, etc.) are computed dynamically by Zoho Analytics from the raw data
- **Our SQLite DB stores the raw data** — these metrics can be computed from our local DB using the same logic
- **Dashboard implication**: The `/api/change`, `/api/cab`, `/api/survey` endpoints return raw rows. Any summary metrics shown on the dashboard should be computed client-side or in additional API endpoints using the formulas documented above.

### 📋 FORMULA REFERENCE FOR DASHBOARD IMPLEMENTATION

If the Node.js server needs to compute any of these metrics locally (from SQLite), use these equivalents:

```javascript
// From change_records table:
const completedCount = db.prepare(`SELECT COUNT(*) as n FROM change_records WHERE status = 'Completed'`).get().n;
const finalizedCount = db.prepare(`SELECT COUNT(*) as n FROM change_records WHERE status IN ('Completed','Cancelled','Rejected')`).get().n;
const changeSuccessRate = finalizedCount > 0 ? (completedCount / finalizedCount * 100).toFixed(1) : null;

// From cab_approvals table:
const approvedChanges = db.prepare(`SELECT COUNT(DISTINCT change_id) as n FROM cab_approvals WHERE approval_status = 'Approved'`).get().n;
const totalChanges = db.prepare(`SELECT COUNT(DISTINCT change_id) as n FROM cab_approvals`).get().n;
const cabCompliance = totalChanges > 0 ? (approvedChanges / totalChanges * 100).toFixed(1) : null;

// Time Elapsed is stored in MILLISECONDS — convert to hours:
// timeElapsedHrs = time_elapsed / 3_600_000
```
