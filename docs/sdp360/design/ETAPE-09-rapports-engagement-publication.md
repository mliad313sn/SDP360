# Dossier de conception — Étape 09 — Générateur de rapports IA, moteur d'engagement, publication externe

Version 1 · 2026-10-19 · Auteur : agent IA · Relecteur : comité (à réceptionner) · Statut : **implémenté (volet agent) — volet humain (serveur d'inférence local, inscription d'application SharePoint, espace de travail Power BI, première campagne de relecture, armement des règles e-mail/Teams) en attente**

## 1. Objectif et périmètre
Produire des **packs de rapport par public** (site · direction · conseil) composés d'un tableau de bord publié (étape 6) : chaque chiffre vient du **même résolveur** que la visionneuse (`services/dashboardData.resolveWidgets`), donc zéro saisie manuelle et zéro écart de chiffre par construction. Une **analyse déterministe** toujours présente (`services/reportAnalysis`, pure, bilingue, ton par public) ; un **commentaire IA** optionnel nourri des seuls chiffres canoniques, vérifié nombre par nombre, anonymisé pour un fournisseur cloud, rejeté vers le texte déterministe au moindre écart (`services/aiCommentary`). Brouillon jusqu'à relecture humaine ; journal de versions = une ligne par génération. Un **moteur d'engagement** : règles d'alerte (métrique, portée, seuil, série, repos, canaux, destinataires), centre de notifications, commentaires, abonnements et résumés, liens de partage signés et expirants avec accusés de lecture, vues intégrables. Une **publication externe** : API REST + OData documentée avec clés par consommateur, quotas et journal ; connecteurs SharePoint (liste Graph), Power BI (flux OData), Teams (carte), e-mail, webhook, Excel planifié — tous passés par l'ordonnanceur commun.

**Hors périmètre agent** : la mise à disposition d'un serveur Ollama (Mistral Nemo) et le réglage de `AI_PROVIDER=local`, l'inscription d'application Microsoft Graph et l'espace Power BI, la rédaction des modèles au-delà des trois livrés, l'armement des canaux e-mail/Teams/webhook sur les règles, la première campagne de relecture (≥ 80 % de commentaires utiles) et la mesure des faux positifs sur 30 jours.

## 4. API
En-têtes de `routes/reportStudio.js`, `routes/engagement.js`, `routes/extApi.js`. Auteur = palier admin ou `report-author` ; un éditeur de site génère le pack de **son** site (`services/userSites`). Lecteur = rapports publiés de ses sites. Publication refusée (409) sans relecture ; rapport publié figé (409). Partage = rôle éditeur, cible dans sa portée ; `GET /share/:token` **sans session**, 404 si expiré/révoqué/épuisé, `?embed=1` pose `frame-ancestors`. API externe = clé `X-Api-Key` (ou `?api_key=`), portées, quota → 429, journal par appel, `X-Quota-Remaining`. OData v4 minimal : document de service, `$metadata` (CSDL), `Metrics`/`Sites`/`Values` avec `$filter` (eq/ne/gt/ge/lt/le + and), `$top` ≤ 5000, `$skip`, `$orderby`, `$select`, `$count`.

## 6. Règles métier
- Un chiffre non mesuré est `null`, affiché « — », jamais 0 ; il compte dans `coverage.total` mais pas dans `coverage.measured` ; il ne déclenche **jamais** une alerte et ne remet pas une série à zéro.
- Analyse : ordre des constats rouge → sites en rouge → dégradation → actions en retard → sous la moyenne flotte → orange → écart entre sites → au-dessus de la flotte → amélioration → non mesuré ; tendance = dernier point contre la moyenne des précédents (bande morte 2 points de %, 10 % relatif sinon) ; « mieux » suit `higher_is_better` du dictionnaire.
- Commentaire IA : liste canonique = toutes les formes d'affichage des chiffres de l'analyse ; années, durées (`13w`, `5 j`) et codes `S1…Sn` tolérés ; tout autre nombre → rejet, texte déterministe, `verified:false` ; fournisseur ≠ `local` → anonymisation avant envoi, restitution après ; `off` → déterministe seul ; une relecture humaine marque `source:'human'`.
- Alertes : déclenchement après `streak` dépassements consécutifs, silence pendant `cooldown_min`, une seule ligne d'état par règle × site (`fleet` pour la flotte) ; `rag_in` ignore `NA` ; une règle désactivée ou un opérateur inconnu ne déclenche jamais ; un webhook/Teams non configuré = saut compté, jamais un échec de tâche.
- Partage : jeton aléatoire 24 octets, stocké haché ; durée bornée 1 h…90 j (défaut 72 h) ; vues max facultatives ; révocation immédiate ; chaque ouverture = un accusé (agent, hachage d'IP tronqué).
- API externe : clé `sdp_…` affichée une fois, stockée hachée ; quota journalier par consommateur (5 000 par défaut) ; au plus 20 métriques par appel ; seuls les **noms de sites** sortent (aucun nom de personne, aucun sujet de ticket).
- Connecteurs : Excel, webhook, SharePoint se sautent chacun sans configuration ; la tâche quotidienne ne tourne que si `publish_cron_enabled='1'` ; les secrets ne figurent jamais dans un résultat ni un journal (`Bearer <token>`).

## 9. Sécurité
Toutes les routes de session dans la matrice d'autorisation ; `/share/:token` et `/ext/*` sont hors session **par conception** et chacun porte son propre contrôle (jeton haché expirant · clé hachée + portées + quota). Secrets (webhooks, secret Graph) en écriture seule et chiffrés par `_SECRET_BLANK_KEEP`. Le HTML des rapports et des vues partagées est échappé ; la vue intégrable pose une CSP propre. Les données envoyées à un fournisseur cloud sont anonymisées et ne contiennent ni nom de personne ni sujet de ticket.

## 10. Exploitation
`/api/sync/health` montre les 6 tâches (optionnelles : « idle » tant que rien n'est configuré). `GET /api/engagement/stats` : règles actives, taux de faux positifs 30 j, utilité des rapports, appels API 7 j. `SELECT category, action, count(*) FROM system_log WHERE category IN ('reports','engagement') GROUP BY 1,2`.

## 11. Risques
- **Compteur de la suite complète non déterministe** (constaté à cette étape, antérieur à elle) : `node --test --test-force-exit` laisse un processus enfant sortir avant d'avoir vidé sa sortie TAP, si bien que le total rapporté varie d'une exécution à l'autre (2 453 à 2 532 pour les mêmes fichiers, 0 échec à chaque fois ; 102/140/153 pour trois fichiers identiques). Les fichiers passent intégralement en isolation. Un échec imprimé est toujours compté ; une sortie tronquée peut en masquer un — à corriger côté runner (fermeture propre des handles plutôt que `--test-force-exit`) dans une étape de dette technique.
- Un fournisseur local lent (CPU) allonge la génération planifiée : la tâche est séquentielle et tolère un échec (repli déterministe) ; surveiller la durée dans le journal des tâches.
- Les lectures OData `Values` résolvent les métriques à la demande : borné à 20 métriques × sites actifs par appel ; un consommateur agressif atteint son quota, jamais la base.
- Les 12 règles livrées visent des métriques du dictionnaire dont certaines sont encore nulles en production (WAN, actifs) : pas de bruit (null ne déclenche pas), mais pas de signal non plus tant que la source n'est pas branchée.
