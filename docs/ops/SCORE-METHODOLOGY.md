# Site score methodology

Generated by `node tools/agent/score-methodology.js` from the code (`--check` fails when a constant changes and this
page was not regenerated). **Nothing here is certified**: no KPI-committee approval is recorded (G06), and the choice of
the reference site score is decision **D-03 — OPEN**.

## 1. Programme score (`services/siteScore.js`, the author's sbDims model)

6 dimensions × 0/1/2 points; score = round(points ÷ 12 × 100). Bands (registry policy `site-score`): GREEN ≥ 70 · AMBER 45–69 · RED < 45.
Window: rolling 3 months ending at the as-of date (`services/scoreWindow.js` rollingWindow, e.g. 2026-03-30 → 2026-06-30).

| Dimension | 2 points (green) | 1 point (amber) | Direction | Definition |
|---|---|---|---|---|
| Reviews (`reviews`) | ≥ 8 | ≥ 5 | higher is better | reviews held · G≥8 A5–7 R<5 |
| Resolution (`resolution`) | ≥ 40 | ≥ 20 | higher is better | resolved ÷ raised · G≥40 A20–39 R<20 |
| Overdue (`overdue`) | ≤ 0 | ≤ 5 | lower is better | overdue issues + actions · G0 A1–5 R>5 |
| Inspections (`inspections`) | ≥ 3 | ≥ 2 | higher is better | inspections run · G≥3 A2 R≤1 |
| Findings (`findings`) | ≤ 0 | ≤ 2 | lower is better | critical+major findings · G0 A1–2 R≥3 |
| Sign-off (`signoff`) | ≥ 70 | ≥ 30 | higher is better | minutes fully signed % · G≥70 A30–69 R<30 |

**Applicability gate** (`hasData`): a site with no measured input on the window is **non applicable** (score, RAG and
trend null), never a graded RED — two dimensions are inverted, so absence of data would otherwise look like excellence.
`raised` (issues raised) is read only to tell a measured 0 % resolution from "no issue raised"; it is never scored.

Certification: not certified — D-01/D-02/D-03 pending.

## 2. Operational composite (`services/siteComposite.js`)

Bands (registry policy `site-composite`): GREEN ≥ 75 · AMBER 55–74 · RED < 55. Formula, quoted from the source:

```js
const del = (100 - odRate) * 0.4 + mttrIdx * 0.3 + (100 - highAging) * 0.3;
const gov = e.e1 * 0.35 + e.e2 * 0.30 + e.e3 * 0.15 + e.e5 * 0.20;
const eng = e.cov * 0.6 + e.nextRate * 0.4;
const score = Math.max(0, Math.round(del * 0.4 + gov * 0.35 + eng * 0.25 - pen))
```

Not per-site isolated: the fleet median resolution time is part of the score. Default anchor date `2026-07-14`. Known
quirks (no ceiling, uncapped penalty, defaults on empty data) are listed at the top of the module and are kept as ported.

## 3. Operational scoreboard (`services/siteScoreboard.js`)

| Dimension | Weight |
|---|---|
| helpdesk | 40 % |
| inspections | 20 % |
| meetings | 20 % |
| assets | 20 % |

Weights are **renormalised over the dimensions present** (a missing dimension is null, excluded — never 0);
coverage = present / 4; no dimension present = non applicable. Bands: `site-composite` (GREEN ≥ 75 · AMBER 55–74 · RED < 55).

Certification: not certified — D-01/D-02/D-03 pending.

## 4. Which score is published

`report_config` `site_score_published_model` — default `legacy` (today: each e-mail keeps its own model). Values: `legacy`, `programme`, `operational`.
The switch only chooses which already-computed result is shown first; the other is carried alongside as "non publié".

## 5. Where the history lives

- KPI definitions and their adoption: `kpi_policies` (migration 065, `services/kpiPolicyStore.js`) — draft → proposed → adopted
  by a committee member who is not the author; adopted versions are immutable; every step appends a history row.
- Governance rules (thresholds of the regulation behaviours): `services/governancePolicy.js`, append-only history
  shown on Admin ▸ Governance policies.
- Switch values: `report_config` (who changed what and when: `updated_by`, `updated_at`), listed in `docs/ops/FLAG-REGISTER.md`.
