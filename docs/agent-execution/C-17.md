## Enforce plan (NOT wired — route by route, each step reversible)

1. Pilot `shadow` on TEST for one reporting cycle; `GET /api/reports/system-log?category=authz` must stay empty
   (any row = a catalogue gap, fix the catalogue, never the guard).
2. Add an `enforce` branch in `authzShadow` that, **per capability listed in an allow-list policy**
   (`authz_enforce_caps`, empty by default), answers from `can()` instead of the legacy guard. Start with low-risk
   read capabilities (`review.read`, `analytics.data.read`, `tracker.read`), then med, then high; `critical`
   capabilities (`platform.identity.manage`, `platform.settings.manage`, `tracker.reset`) last, after C-18 grants exist.
3. Only once C-18/C-19 add grant expiry / qualifications / SoD does `can()` differ from the legacy guard — each such
   denial must first be observed in shadow before the capability enters the enforce list.
4. Inline checks (`scope.all_sites`, `site.records.edit`, …) move to `can(user, cap, {siteId})` handler by handler,
   with the existing site-scope tests as the oracle.

## Deviations

- `requires_request` flags (identity, settings, governance role assignment, finance read) are a **proposal**, not an
  approved sensitive-role list (human gate). `prereq` is empty everywhere (no qualification kinds decided).
- Inline-check capabilities are coarse (one per role tested inside handlers); the matrix columns show where.
- `enforce` is read as `shadow` (one warning in the log) rather than refused, so a premature switch can't lock anyone out.
- The mode is cached 30 s per process (a config change takes ≤ 30 s).
