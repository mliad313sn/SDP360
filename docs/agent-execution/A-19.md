## A-19b — PVs
- Migration `db/postgres/meetings/051_soft_delete.sql` (also applied by `initPgMeetings`).
- `meetings-db.js`: every `md_meetings` reader (list/count/get/status, issues log, actions register, insights,
  aggregate, compliance, previous meeting / pre-brief, contacts, score inputs, monthly summary, export, parent
  lookups) filters `m.deleted_at IS NULL`; issues/actions/projects of a deleted PV are kept and hidden through the join.
  `saveMeeting` refuses (409 CONFLICT) a save that resolves to a soft-deleted PV by id, reference or month fallback.
  `services/reviewData.js` meetings readers filtered. Delete route logs `meeting_deleted` / `meeting_soft_deleted`;
  `POST /api/meetings/:id/restore` (admin tier) logs `meeting_restored`. Trash + purge register the `meetings` module.
- The reader guard found two unfiltered `insights` queries (LEFT JOIN layout) that the first pass missed.
- Tests: `soft-delete-meetings` (5), `soft-delete-routes.smoke` (+2), guard extended to `meetings-db.js`.

## Deviations
- Migration numbers: the coordinator assigned 049/051/052. They are placed in each module's own area
  (`inspection/049`, `meetings/051`, `reports/052`) instead of `inspection/002` / `meetings/003` / `reports/043` named by
  the goal (043 is taken), so the columns land in the area that creates the table and no parallel worker collides.
- The reader guard scans `FROM`/`JOIN` reads; write statements (UPDATE/INSERT) are guarded by the routes resolving the
  parent through a filtered reader first (404 on a deleted parent).
- `tools/pilot/pilot-metrics.js` (a standalone read-only report tool) is not filtered: it tolerates missing columns
  against arbitrary databases; listed for a person to decide.
