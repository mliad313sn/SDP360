## A-19b — PVs

## A-19c — portfolio nodes + cadences
- Migration `db/postgres/reports/052_portfolio_soft_delete.sql` (7 portfolio tables + `meeting_cadences`).
- `services/governanceStore.js`: `portfolio()` reads every kind live and drops children whose parent chain holds a
  deleted node (programme → objective → project → plan elements; task → parent task); `projectDetail`/`getProject`/
  `planRow`/`gateCounts`/`setProjectSites`/`moveProjectStage` treat a deleted project (or ancestor) as missing;
  editing a deleted node by id → 409. `listCadences`/`getCadence`/`listSessions`/`getSession`/`openSessionActions`

  `routes/governanceRoles.js` seat check ignores deleted cadences.

## Deviations
- Migration numbers: the coordinator assigned 049/051/052. They are placed in each module's own area
  (`inspection/049`, `meetings/051`, `reports/052`) instead of `inspection/002` / `meetings/003` / `reports/043` named by
  the goal (043 is taken), so the columns land in the area that creates the table and no parallel worker collides.
- The reader guard scans `FROM`/`JOIN` reads; write statements (UPDATE/INSERT) are guarded by the routes resolving the
  parent through a filtered reader first (404 on a deleted parent).
- Governance soft deletes are logged under the existing `governance` category (the route's own logger, kept so
  governance events keep their 7-year retention); restores and purges use the `portfolio` category.
- Restoring a child whose parent is still deleted succeeds but the child stays hidden until the parent is restored.
- `tools/pilot/pilot-metrics.js` (a standalone read-only report tool) is not filtered: it tolerates missing columns
  against arbitrary databases; listed for a person to decide.
