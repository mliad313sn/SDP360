## 2. New break attempts this round (claim · attack · outcome), aimed at code changed by fixes 21, 22 and 24

**R6-A1: activation tool in Policy Center mode (fix 22 N-15 + fix 24): requester impersonation. BROKEN.** Claim (`activate-switches.js:45-52`, PLAN-PILOTE:91-97): with the center on, the tool "files one Policy Center request per key … requested by the --operator account, which must be an active super_admin; a second super_admin decides". Attack (`/tmp/claude-0/p11attack-r6/tests/r6imp.test.js`, real server, PG, center ON, two long-standing super_admins). The person who is really running the CLI is pc_super. They call `main(['--apply','--lots=L03',…,'--operator=pc_super2'])`, which files request `pc-1` for `portfolio_editor_plan_writes` **as pc_super2**. pc_super then approves `pc-1` in the center → **200 "approved", value 1**. One person both filed and approved a four-eyes change. The record names a colleague as the requester, and `operatorAccount()` (`activate-switches.js:433-438`) is only a username lookup with no authentication. The policy request carries neither the OS user nor the host: those go into the rollback file only, and no rollback file is written when every step goes to the center (`:563`). The precondition is shell access and the DB URL on the server, so a direct `UPDATE report_config` is already possible for this person. The impact is therefore a **forged four-eyes record** (a falsified "second person" trail), not an escalation of privilege. A related point holds with the center off: `--second-operator` is a free-text name, checked only for being a different spelling (`secondOperatorRefusal`: `alice` vs `bob`, `alice.x`, `a1ice` are all accepted). It is never authenticated and never checked to be a super_admin. PLAN-PILOTE:93 says "nomme une **autre** personne, qui a relu le plan" (names another person who reviewed the plan), which the tool cannot verify.

**R6-A2: audit chain anchors (fix 24): default (unhardened, no env pin) state. HOLDS as documented, gaps found.** Claim (EXPLOITATION.md:89-93, `auditChain.js:6-13`): a tail delete, a TRUNCATE, a rewrite or a swap for an empty copy "no longer verifies as ok". Attack (`r6chain.test.js`). (a) Without `SDP_LEDGER_SCHEMA`, a session whose search_path starts with a schema holding empty copies of all 12 ledgers gets **`ok:true`**, `schema = r6_shadow_*`, **`anchors:false`**. `current_schema()` becomes the shadow, the anchor table is not found, and the anchor check is skipped without any signal. (b) With only one ledger missing from the shadow schema, that ledger reports `ok:null` "not verifiable", and the overall `ok` is still **true**. (c) Forged anchor: the app role keeps INSERT on `audit_chain_anchors` even after hardening. Inserting `row_count=999` raises a false alarm (DoS of the nightly job). Inserting `row_count=0, last_id=NULL` resets the comparison baseline, and `verify` then returns `ok:true` (`lastAnchor` = highest id; anchors are not chained). Once hardened, (c) only resets a baseline over a ledger the app role can no longer delete from. (a) and (b) are named in the ADR as residuals that the env pin and the hardening close. No `.env` template or installer step sets `SDP_LEDGER_SCHEMA` (grep: only docs and `RACI-TEMPLATE.md` mention it). Verdict: the detection claim holds only in the hardened + pinned configuration. In the default configuration, the verify fails open on a missing anchor table and on unverifiable ledgers.
