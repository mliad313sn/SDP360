## Defect found and fixed

**Stored secrets returned to the browser by the settings routes** (`routes/adminConfig.js`):
- `GET /api/reports/config` blanked a hand-written list of secret keys that had drifted from the secret set:
  `sharepoint_client_secret`, `engagement_teams_url`, `engagement_webhook_url`, `publish_webhook_url` came back
  **decrypted**.
- `PUT /api/reports/config` answered with `setConfig`'s return value = the full, **decrypted** config → every
  stored secret (SMTP password, SSO client secret, Meridian/Meraki/OpManager keys…) came back on every save.

Fix (smallest): one `redactSecrets()` that blanks every key of `reportConfig._SECRET_BLANK_KEEP` (the same set
that is encrypted at rest and blank-kept on save) and keeps `opmanager_ca_bundle_set`; used by GET and PUT.
No page reads those values (the admin cards already blank their secret inputs). Regression test:
`tests/reporting-routes.smoke.test.js` "C-23: every stored secret is blanked on GET and in the PUT answer" —
**red before the fix** ("smtp_pass leaked in the PUT answer"), green after; I7 was red on the GET leak first.

**access.html asked a route that does not exist for the caller** (found by the full e2e run: the existing V1
viewport journey was RED on the base branch — 4 console errors "404 (Not Found)" on access.html at every width).
Since C-22 the page always called `GET /api/access/emergencies`, which answers 404 while
`emergency_access_enabled='0'` (default) and 403 for anyone not super_admin — so every visit logged a failed
request. Fix: `GET /api/access/me` now carries `emergency_enabled` (true only for a super_admin with the switch
on) and `public/access.js` calls the emergency list only then. Regression: `tests/access-routes.smoke.test.js`
(plain session → false), `tests/emergency-access.smoke.test.js` (off → false; on + super_admin → true; plain
session → false), and V1 back to green.
