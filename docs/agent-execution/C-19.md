# C-19 — Qualification evidence + separation-of-duties registry + R7 approver rule

Goal row: PLAN-V3 V4b · findings G41 G43 · migration 059 · switch `qualification_check_enabled` (`0`) ·
PO decisions R7 (who approves access), R8 (SoD per object), R10 (qualification kinds) of
`docs/decisions/2026-11-05-PO-DELEGATED-DECISIONS.md`.

## What was built
- **059_qualification_evidence.sql** — `qualification_kinds` (editable, seeded `site-induction`,
  `electrical-authorisation`, `working-at-height`, `confined-space`) and `qualification_records` (user, kind, issuer
  text, issued/expiry dates, evidence reference, recorded_by/at, verified_by/at, status recorded → verified | rejected,
  → revoked). A CHECK constraint keeps the verifier distinct from holder and recorder at database level too.
- **services/qualificationPolicy.js** (pure) — record validation (issuer + evidence reference required, sane dates),
  `verifyCheck` (admin tier; holder, recorder and their deputies refused through sodPolicy), `stateOf`
  (valid only when verified and not expired), `evaluate(required, records, today)` → missing / expired / unverified
  with a readable reason, `requirementsFor(cap)` = catalogue `prereq` ∪ report_config `qualification_requirements`.
- **services/qualificationStore.js** — kinds, records, verify/reject/revoke (system_log `identity`), `checkCapability`
  and a `gate(capId)` middleware. **`qualification_check_enabled='0'` (default) = today: nothing is ever refused.**
  `'1'` → a capability with a declared requirement is refused 403 with the reason (“… — SDP360 records evidence only;
  ask your site HSE owner”). The gate sits on field capture (`PUT /api/field/outbox/:uuid`, `POST /api/field/uploads`)
  and does nothing until a requirement is declared (none is, today). `authorizationService.can` gained the
  `qualification_*` denial when the caller passes `ctx.qualification`.
- **services/sodPolicy.js** (pure, G43 · R8) — one registry: `no_self_approval`, `no_self_verification`,
  `no_deputy_verification`, by object (`access.decide`, `qualification.verify`, plus the handoff / commitment /
  governance rules listed where they already live), `POLICY_VERSION` hash. The watched pair `report-author` + approver
  of the same report is a **warning only** (`report.approve`). No platform-level role-pair conflict. Reused by
  `accessRequestLifecycle.check` and `qualificationPolicy.verifyCheck`.
- **services/accessApproverPolicy.js** (pure, R7) + report_config `access_approver_policy` (editable JSON; unreadable →
  default): platform roles (admin, executive, super_admin, tracker-admin, audit-viewer) by a super_admin; any other role
  by an admin-tier user holding every site the request names (else the subject's sites; no site → super_admin only).
  `accessStore.decide/approvalsFor` apply it; `GET /api/access/approvals` and `/me.can_approve` open to the admin tier;
  an R7 approver may read the request. Revoke stays super_admin. This widens C-18's super_admin-only rule.
- **Routes** `routes/qualifications.js` (on the access router): kinds (read: session; write: super_admin, catalogued
  `platform.reference_data.manage`), records (own; admin tier for others), record/verify/reject/revoke, `check?cap=`.
  Every error through `httpError.fail`. `docs/ops/AUTHZ-MATRIX.md` regenerated (546 routes).
- **UI** — Qualifications tab on `access.html` (EN/FR self-translated) with the “evidence only, never a physical
  authorisation” text, the record form (admin tier) and verify/reject/revoke buttons.

## Deviations
- No qualification events table (status columns + system_log carry who/when); the audit chain is unchanged.
- `qualification_requirements` (default `{}`) was added as the editable place to declare which capability needs
  which kind, since the catalogue's `prereq` lists are empty and choosing them is a human decision.
- An unreadable configuration keeps the last value read by the gate (never read = off); an unreadable record table
  while the check is on returns an error.
