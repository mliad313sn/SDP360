1. Objectif & périmètre

Transformer les alarmes d'OPManager en tickets SDP actionnables et auto-classés, pour rendre l'IT proactif — agir avant que l'utilisateur ne remonte le problème — sans noyer le service desk sous des tickets bruités.

Trois résultats attendus :

  • Proactivité : un incident d'infrastructure (lien WAN, onduleur, serveur critique) ouvre un ticket routé au bon groupe du site dès la détection, avant l'appel utilisateur.
  • Qualité de donnée Risk Register : le ticket porte déjà le champ « Services affected » (Internet · Mobile · Électricité · Infrastructure · Radio) — l'occurrence Risk Register se classe toute seule, là où aujourd'hui la classification est majoritairement manuelle / vide.
  • Discipline : le ticket est la fonction de forçage qui garantit qu'aucun incident infra ne se perd, avec un SLA mesurable par site.

Hors périmètre de ce document (sous-projets voisins, mêmes fondations) : le pipeline « leaver » MyPath → SDP → ADManager Plus (SP-A) et les tickets sécurité ADAudit Plus. Leur faisabilité est confirmée ici (§3) mais leur conception fait l'objet de documents dédiés.

2. Architecture cible (hybride on-prem / cloud)

La pile est hybride : OPManager, ADAudit, ADManager Plus, l'Active Directory et ce dashboard vivent sur le LAN ; ServiceDesk Plus est dans le cloud. Le dashboard, seul composant qui parle à SDP Cloud et vit sur le LAN, est le broker on-prem + cerveau de corrélation.

Deux chemins techniques sont possibles — et le bon choix dépend du besoin de pré-tag Risk Register :

Chemin A — Intégration native « Log a Ticket → SDP Cloud » baseline

Alarme OPManager → Profil de notification « Log a Ticket → ServiceDesk Plus Cloud » (OAuth Zoho) → Requête SDP créée depuis le « Default Request Incident Template » (device → CI) → réouverture si l'alarme resurgit

Avantage : zéro code, livré par l'éditeur. Limite : le template natif mappe un jeu de champs fixe (priorité, département, sévérité, groupe) — il ne permet pas de poser de façon fiable un champ multi-select spécifique (le « Services affected » du Risk Register) dérivé de la catégorie d'alarme. C'est donc le socle rapide, pas le porteur du pré-tag.

Chemin B — Webhook OPManager → broker dashboard → API SDP Cloud recommandé pour le pré-tag

Alarme OPManager (critique, soutenue, dédupliquée) → Profil « Invoke a Webhook » (POST JSON, variables d'alarme) → Broker dashboard (on-prem) : • résout site → groupe via notre mapping (sites.zoho_group) • dérive « Services affected » depuis la catégorie d'alarme (→ domaine Risk Register) • déduplique contre nos propres données → POST /api/v3/requests SDP Cloud (champ multi-select pré-rempli + groupe) → (option) N × POST .../tasks : fan-out par équipe applicative → au rétablissement : webhook « on-clear » → clôture la requête via l'API

Avantage : contrôle total du payload → le pré-tag Risk Register est possible, plus notre corrélation maison. Coût : une route broker à écrire et à sécuriser (elle réutilise notre pile OAuth Zoho existante).

Décision d'architecture. Puisque tu veux le pré-tag Risk Register, le Chemin B est le porteur principal. Le Chemin A reste le socle de démarrage (Phase 1) pour prouver le tuyau et le comportement d'auto-clôture avant d'écrire le broker (Phase 2).

4. Matrice de sélection des événements (anti-surcharge)

« Tout ticketiser » tue un service desk. Règle directrice ITIL Event Management : seuls les événements Exception (impact métier) ouvrent un ticket. Informational et Warning restent en alerte/tableau de bord.

Les 6 filtres entre l'alarme et le ticket

  1. Gating de sévérité — seulement Critical/Trouble, jamais Info/Warning.
  2. Durée soutenue / anti-flapping — l'alarme doit persister N sondes consécutives (≈ intervalle × 2-3, soit ≥ 3-5 min pour l'infra critique) : un flap de 30 s ou une sonde ratée n'ouvre rien.
  3. Déduplication — plusieurs symptômes d'un même incident → un ticket racine.
  4. Corrélation parent-enfant — une panne amont (lien WAN, routeur cœur) supprime les alarmes des équipements aval. Le levier n°1 pour un réseau minier hub-and-spoke.
  5. Fenêtre de maintenance — alarmes supprimées pendant les interventions planifiées ; sauter si l'alarme est acquittée.
  6. Auto-clôture — le ticket se ferme quand l'alarme se rétablit (bidirectionnel).

Schéma de paliers — NOC central + sites miniers distants

PalierClasses d'équipementDéclencheur ticketPriorité
T1 — auto-ticketRouteurs/switchs cœur & distribution · liens WAN/MPLS/VSAT · onduleurs/énergie/environnement · serveurs & services critiques (AD DC, DNS, DHCP, hyperviseurs, app/DB core) · pare-feux/VPNDown / critique, soutenu ≥ 3-5 min, avec suppression avalP1 / P2

T3 — pas de ticketPorts switch d'accès / interfaces individuelles · postes/portables utilisateurs · pics CPU/mémoire/latence transitoires · AP Wi-Fi isolé · événements informationnels · équipements en maintenanceTableau de bord / notification seulement (le desk arrive par l'utilisateur)—

Checklist par règle d'alarme (répondre OUI à tout avant d'autoriser l'auto-ticket)

  1. Sévérité Critical/Trouble (Exception), pas Info/Warning ?
  2. Palier T1 ou T2 (équipement partagé/infra), pas un poste/port d'accès ?
  3. Soutenu ≥ N sondes / N minutes ?
  4. Dédupliqué (suppression des doublons active) ?
  5. Corrélé (l'équipement est dans la carte de dépendances) ?
  6. Conscient de la maintenance (respecte la fenêtre + acquittement) ?
  7. Actionnable & assigné (un humain doit agir, groupe/priorité clairs) ?
  8. Auto-clôturable au rétablissement ?

Une règle qui échoue à #1, #2 ou #7 → tableau de bord seulement.

5. Pré-classement automatique du Risk Register

OPManager connaît la nature de l'alarme (catégorie / type d'équipement). Le broker (Chemin B) traduit cette nature en valeur(s) du champ SDP « Services affected », qui correspond 1:1 aux 5 domaines du Risk Register déjà en place (risk-register-export.js). L'occurrence se classe sans geste humain — exactement la donnée aujourd'hui majoritairement absente.

Passerelle GSM / 3G-4G / SIMMobileIndisponibilité téléphonie mobile

Serveur/service core (AD DC, DNS, DHCP, mail, DB, hyperviseur), pare-feuInfrastructureIndisponibilité infrastructure
Contrainte technique. Les valeurs posées via l'API doivent pré-exister comme options du champ multi-select SDP. Il faut donc garder en phase le vocabulaire « Services affected » côté SDP et notre table de domaines Risk Register — une table de correspondance versionnée dans le broker.

6. Cycle de vie du ticket

1. DÉTECTION Alarme critique, soutenue, dédupliquée, hors maintenance 2. ENRICHIS. Broker : site→groupe · Services affected→domaine RR · dédup 3. CRÉATION POST /api/v3/requests (priorité selon palier, groupe, UDF pré-rempli, CI) 4. ROUTAGE Assignée au groupe technicien du site/bureau (payload explicite) 5. (OPTION) Fan-out de tâches par équipe applicative si pertinent 6. VIE Changements de sévérité → notes (pas de nouveau ticket) 7. CLÔTURE Rétablissement → auto-clôture (natif on-prem) ou webhook on-clear (Cloud) 8. PREUVE Occurrence Risk Register auto-classée ; SLA de traitement mesuré

7. Plan d'implémentation progressif

Principe : commencer très petit, prouver, élargir. Chaque phase est additive et réversible ; on ne passe à la suivante que si les critères de sortie sont verts.

Phase 0 — Prérequis & validation du risque ouvert

  • Vérifier : SDP Cloud Enterprise, build OPManager, rôles, HTTPS sortant, bon DC Zoho.
  • Établir l'app OAuth Zoho (réutiliser la pile existante ; ajouter le scope requêtes).
  • Tester explicitement l'auto-clôture au rétablissement sur le Cloud (le seul point non documenté) sur un équipement de labo.

Sortie : prérequis confirmés + verdict clair sur l'auto-clôture Cloud (native OK, ou repli webhook on-clear retenu).

Phase 1 — Socle natif (Chemin A)

  • Un seul site, une seule classe T1 (ex. lien WAN + onduleur), profil natif « Log a Ticket → SDP Cloud ».
  • Activer dédup + suppression parent-enfant + fenêtre de maintenance + gating sévérité.
  • Prouver en réel : auto-ticket, routage, réouverture, auto-clôture (ou webhook on-clear).

Sortie : le tuyau fonctionne en prod sur un périmètre minuscule, zéro flot parasite.

Phase 2 — Broker + pré-tag Risk Register (Chemin B)

  • Écrire la route broker (dashboard) : « Invoke a Webhook » OPManager → enrichissement → API SDP Cloud.
  • Poser le champ « Services affected » depuis la catégorie d'alarme ; routage site→groupe via notre mapping ; dédup contre nos données.
  • Valider que l'occurrence Risk Register se classe automatiquement.

Sortie : tickets auto-classés Risk Register sur le périmètre pilote ; corrélation maison en place.

Phase 3 — Extension paliers & sites

  • Étendre à tous les T1 puis T2, site par site ; caler les seuils de durée par intervalle de sonde.
  • Synchroniser les fenêtres de maintenance ; ajouter le fan-out de tâches là où c'est pertinent.

Sortie : couverture infra complète, volume de tickets maîtrisé (mesuré, cf. §9).

Phase 4 — Corrélation & scorecard de proactivité

  • Fusionner les signaux (OPManager + SDP + inspections + AD) en un score « site à risque » sur le dashboard.
  • Publier la scorecard de proactivité (temps d'accusé, tickets évités par dédup, % occurrences RR auto-taggées).

Sortie : le dashboard alerte le SDM avant la crise — la valeur que seul lui apporte.

Rollback. Chaque phase est additive et réversible : désactiver le profil de notification (Chemin A) ou la route broker (Chemin B) suffit — aucune modification destructive de SDP ni du dashboard. On peut arrêter à n'importe quelle phase sans dette.

9. Métriques de succès

  • Tickets auto-créés / auto-clôturés par palier et par site.
  • Ratio de dédup (alarmes reçues ÷ tickets créés) — mesure directe de l'anti-surcharge.
  • % d'occurrences Risk Register auto-taggées (vs saisie manuelle) — le gain de qualité de donnée.
  • MTTA (temps moyen d'accusé) sur les tickets auto-créés.
  • Taux de faux tickets (créés puis clos sans action) — doit tendre vers zéro ; sinon resserrer les seuils.
