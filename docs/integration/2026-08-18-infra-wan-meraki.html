1. Objectif & périmètre

Donner à l'IT une vision fiable de la disponibilité & qualité WAN par site et par lien (WAN1/WAN2), alignée sur les chiffres que Meraki affiche lui-même, et en tirer deux usages : (a) l'auto-remplissage des KPIs infra du rapport hebdo/mensuel, et (b) un instrument SLA / refacturation ISP défendable (crédit de service contractuel), là où l'ISP ne fournit aucun rapport.

Hors périmètre : LAN/WLAN/Serveurs (couverts par OpManager → Analytics Plus, sous-projet voisin) ; SLA de réponse helpdesk (Phase 2) ; sites hors fuseau UTC.

2. Architecture (deux instruments distincts)

Le WAN alimente deux instruments séparés qui ne se mélangent pas :

Meraki Dashboard API (lecture seule) │ ├─► [A] WAN Health + Auto-fill rapport → disponibilité "% Time Up" fidèle Meraki (dérivée loss/latence) │ table wan_link_snapshots → cartes WAN Health + cellules Infra du rapport hebdo/mensuel │ └─► [B] SLA / Refacturation ISP → coupures totales dans l'horaire de service → crédit % du MRC table wan_outages → vue Chargeback + export de preuve (le rapport que l'ISP ne donne pas)

[A] répond à « le lien est-il sain, quel est le % de dispo ? » (opérationnel). [B] répond à « combien de temps l'ISP nous doit-il un crédit ? » (contractuel, mesuré uniquement dans l'horaire de service, cible SILVER 97 %).

3. Comment Meraki calcule la disponibilité — sourcé

Point crucial vérifié dans la documentation officielle Meraki, pour reproduire exactement ses chiffres dans le rapport :

  • Meraki ping une destination (par défaut 8.8.8.8, configurable sous Security & SD-WAN → SD-WAN & Traffic Shaping → Uplink Statistics) toutes les secondes.
  • Un lien est DOWN quand il voit 100 % de perte de paquets pendant 5 minutes vers la destination primaire.
  • Nuance : 100 % de perte vers une destination alternative mais pas la primaire → signalé visuellement mais PAS compté « down ».
  • « % Time Up » = fraction du temps non passée dans cet état down, pendant que le MX est en ligne.
Conséquence favorable. Le « % Time Up » du Summary Report est donc dérivable du getDeviceLossAndLatencyHistory (documenté, fiable, gratuit) — pas besoin de l'event-log (non documenté) ni de la licence Insight. Il suffit de dériver avec la même règle que Meraki (voir §6) puis de calibrer contre le Summary Report.

6. Écarts à corriger pour être « exactement comme Meraki »

La dérivation V1b actuelle diverge de la méthode Meraki sur 3 points (c'est ce qui a produit l'écart 100 % chez nous vs 22 % chez Meraki sur un lien dégradé) :

Notre dérivation V1bMeraki (documenté)Correction
Résolution 1 heureping/seconde, décision sur fenêtre 5 minRésolution ≤5 min — sinon une heure à 17 % masque les fenêtres 5 min à 100 %
« up si UNE destination répond » (min sur toutes)décision sur la destination primaire seuleUtiliser la primaire, pas le min sur toutes
« down ssi loss = 100 % » par intervalledown = 100 % soutenu 5 minDown = 100 % soutenu ≥5 min
Puis calibration. L'agrégation fine du « % Time Up » n'est pas publiée par Meraki → après les 3 corrections, on cale les bords via tools/meraki/calibrate.js contre le Summary Report (ex. Ity 99.86 / 97.87). C'est la gate qui valide « fidèle à Meraki ».

7. Prérequis & gates d'activation (côté client — clés en ENV, jamais affichées)

  1. Clé API Meraki + Org ID (numérique, pas l'URL /o/<slug>) — renseignés dans Admin → Infra.
  2. Mapping Site ↔ network Meraki + sous-sites Exploration (éditable dans l'admin, sans déploiement).
  3. Destination de monitoring primaire cohérente sur chaque MX (celle qui décide le down).
  4. Découverte : probe sur l'org réel pour trancher (a) l'event-log émet-il des uplink up/down + types + rétention ; (b) Insight couvre-t-il les MX ; (c) la dérivation loss calibrée reproduit-elle le Summary Report.
  5. Calibration : lancer calibrate.js, régler meraki_missing_policy.
  6. SLA : mapper circuits (uplink→ISP, calendrier horaire par site, MRC, contact ISP) + armer la notif 15 min.
  7. Webhook (Phase 3, optionnel) : pointer l'alerte « WAN Uplink status » vers l'endpoint dashboard pour la capture temps-réel des coupures SLA.

8. Plan d'implémentation progressif

Phase 0 — Découverte & calibration gate

Probe org (event-log / Insight / loss-fidélité) + calibration contre le Summary Report. Ne dépend pas de dev neuf — dépend de la clé Meraki (client). Livrable : décision de source (loss calibré ✓ par défaut, Insight ou webhook si disponibles).

Phase 1 — Dispo « fidèle Meraki » pour le rapport recommandé

Corriger la dérivation (résolution ≤5 min + destination primaire + 100 %-5 min), calibrée. Alimente WAN Health + l'auto-fill hebdo.

Phase 2 — Auto-fill mensuel + sélecteur de dates

Câbler l'auto-fill mensuel (fenêtre mois coupée aux jours écoulés, plus d'artefact « fraction du mois »). Ajouter le sélecteur last day / last week / custom sur WAN Health pour réconcilier avec un custom range Meraki identique.

Phase 3 — SLA temps-réel par webhook (optionnel)

Basculer la capture des coupures SLA du polling vers le webhook Meraki « WAN Uplink status » (transitions horodatées, poussées, sans rétention à gérer).

9. Garde-fous, risques & rollback

  • Tout config-gaté + best-effort : sans clé Meraki, tout est inerte ; un échec de collecte garde les snapshots précédents.
  • Deux instruments séparés : le SLA ne touche ni WAN Health, ni wan_link_snapshots, ni les decks PPTX.
  • Notif ISP armée-OFF par défaut : aucun envoi tant que l'admin n'a pas renseigné le contact + coché l'arme ; jamais d'envoi après rétablissement.
  • Rollback : additif et réversible — retirer la clé / désactiver l'arme suffit, aucune modification destructive.
  • Risque principal (attribution) : « uplink down » mesuré côté MX ≈ circuit ISP, mais un ISP peut contester (électricité last-mile, démarcation). Garde-fous : exclusion wan1+wan2 simultané, fenêtres de maintenance, export de preuve. Le contrat gouverne le chiffre liant.
