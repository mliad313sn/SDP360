1. Objectif & parti pris d'architecture

Centraliser et fiabiliser les actions d'identité et de sécurité AD — pour que le technicien du site agisse en un clic gouverné, sans rien oublier, sans jamais détenir de privilège élevé, et sans quitter les outils qu'il utilise déjà.

Parti pris (validé) : on ne reconstruit pas une console d'action maison. L'action d'identité se fait nativement dans le ticket SDP, exécutée par ADManager Plus (délégation + approbation + audit). Le dashboard n'est pas le bouton d'action — il est la couche de supervision et de corrélation au-dessus (complétude « rien ne se perd », SLA, corrélation leaver→matériel, digests d'hygiène AD). Ce parti pris respecte l'investissement outillage et colle à la réalité réseau (VPN site-à-site vers les outils on-prem).

Lot de ce document :

  • A1 — Désactivation d'un leaver (le besoin actuel) : ticket MyPath → approbation → clic « Disable » dans le ticket.
  • A2 — Reset mot de passe / déverrouillage : faible risque, gros volume déflecté — le gain rapide.
  • B1 — Connexion d'un compte désactivé : ticket sécurité immédiat (signal fort).
  • B2 — Comptes dormants : digest hebdomadaire par site (pas un ticket par compte).

Le provisioning joiner (A3) et les autres événements sécurité (changement de groupe privilégié…) sont en feuille de route, hors lot v1.

3. Connectivité SDP Cloud → ADManager Plus on-prem (derrière le VPN)

SDP est Cloud ; ADManager Plus est on-prem, derrière le VPN site-à-site. Le pont officiel et recommandé est le modèle « probe » :

Technicien (sur le VPN) ── clic « Disable » dans le ticket ──▶ SDP Cloud │ │ (la sonde interroge le cloud toutes les ~5 min — SORTANT uniquement) ▼ Probe SDP Cloud (installée on-prem, à côté d'ADManager Plus) │ HTTPS 443 SORTANT vers SDP Cloud ; relaie les appels REST en LAN ▼ ADManager Plus on-prem ── écrit dans AD (compte de service délégué, audité)
  • Sortie seule : la sonde initie une connexion HTTPS 443 sortante vers SDP Cloud ; rien n'est ouvert en entrée vers le réseau on-prem. ADManager Plus n'est jamais exposé à Internet. C'est le modèle VPN-friendly.
  • Prérequis : ADManager Plus build ≥ 7064 ; l'Authtoken admin/technicien ADMP saisi côté SDP Cloud ; la sonde co-localisée avec ADMP.
  • À éviter : l'ancien modèle « exposition Internet » (DMZ / héberger ADMP sur AWS/Azure) — inutile et moins sûr dès qu'on utilise la sonde.
À vérifier en tenant. La documentation publique est incohérente entre le modèle sonde (actuel) et le modèle DMZ (ancien) — confirmer que votre build relève du modèle sonde, et le port du saut sonde→ADMP (probablement console ADMP 8080/8443, à n'ouvrir qu'en LAN/VPN, jamais sur Internet).

5. Le lot de cas d'usage (A1 · A2 · B1 · B2)

A1 — Désactivation d'un leaver flagship

MyPath (leaver) → ticket SDP → Business Rule : routage groupe du site → (Workflow ADMP : approbation) → le technicien clique « Disable » DANS le ticket → ADManager Plus exécute (délégué, audité) → ADAudit Plus atteste la désactivation → fan-out de tâches SDP aux équipes applicatives (révocation d'accès) Dashboard : board de complétude + SLA de désactivation par site + corrélation leaver→assets

A2 — Reset mot de passe / déverrouillage gain rapide

Ticket (ou self-service) → le technicien reset/unlock depuis le ticket → ADManager Plus. Faible risque, gros volume déflecté — idéal pour démarrer et prouver l'action native in-ticket + l'audit. Dashboard : métriques de volume et de déflexion.

B1 — Connexion d'un compte désactivé sécurité — immédiat

Alerte native ADAudit Plus « Disabled Users Logon Attempt » → ticket SDP immédiat au groupe sécurité/technicien du site → investigation. Signal à fort ratio signal/bruit (rare et grave). Dashboard : flux des événements sécurité par site.

B2 — Comptes dormants hygiène — digest

Rapport d'inactivité ADAudit Plus → digest hebdomadaire par site (réutilise le patron send-hygiene déjà en place) listant les comptes dormants avec liens profonds pour agir → le technicien revoit et désactive via l'action in-ticket. Jamais un ticket par compte — un digest par site. Dashboard : générateur du digest + liste par site.

6. Matrice anti-surcharge ADAudit (immédiat vs digest)

Même discipline que pour OPManager : ticket immédiat uniquement pour les vrais signaux sécurité ; digest par site pour l'hygiène. Sinon on noie le service desk.

Événement ADAudit PlusModeNature
Connexion d'un compte désactivé (B1)Ticket immédiatSécurité — signal fort
Changement de groupe privilégié (Domain Admins…) roadmapTicket immédiat de revueSécurité — très sensible
Échecs d'authentification répétés / lockoutsImmédiat si seuil franchi, sinon digestSécurité / brute-force
Comptes dormants (pas de logon N jours) (B2)Digest hebdo par siteHygiène
Comptes jamais connectés / actifs après création roadmapDigestHygiène (trou d'onboarding)
password-never-expires / not-required (actifs) roadmapDigestHygiène

Règle : un événement qui n'exige pas d'action humaine immédiate → digest, jamais un ticket unitaire. Le digest est dédupliqué et groupé par site.

7. Colonne vertébrale sécurité (anti-usurpation)

  1. Pas de compte god dans le dashboard. Il ne fait que lire/agréger. L'écriture AD passe uniquement par ADManager Plus.
  2. Moindre privilège délégué : le technicien agit via ADManager Plus, restreint à ses OU ; ses droits AD natifs restent inchangés — le compte privilégié vit seulement dans ADMP.
  3. Approbation avant exécution : Workflow ADManager Plus barre l'action tant qu'elle n'est pas approuvée (à confirmer sur le chemin ticket — §9).
  4. Step-up / 2FA au moment de l'action : 2FA technicien ADManager Plus (6 méthodes). Pas de MFA maison. Option : re-challenge via le SSO Entra déjà codé (dormant) du dashboard si un déclenchement passe par lui.
  5. Double preuve : ADManager Plus journalise l'action, ADAudit Plus atteste le changement dans AD — qui/quoi/quand, des deux côtés.

8. Plan d'implémentation progressif

Principe : commencer par le moins risqué, prouver, élargir. Chaque phase est additive et réversible.

Phase 0 — Prérequis & validation des zones grises

  • Déployer/confirmer la sonde (sortie seule) ; ADManager Plus ≥ 7064 ; Authtoken ; port sonde→ADMP en LAN.
  • Vérifier que l'approbation Workflow s'interpose sur une action initiée depuis le ticket (la plus grosse hypothèse).
  • Confirmer : tuile unlock dans le plugin, 2FA sur le rôle délégué OU, plafond de licences REST.
  • Test labo : une désactivation de bout en bout depuis un ticket, approuvée + 2FA + auditée.

Sortie : connectivité prouvée, comportement d'approbation-sur-ticket tranché.

Phase 1 — A2 reset / unlock (le moins risqué)

  • Un site : action reset/unlock in-ticket via ADManager Plus, avec 2FA + audit.
  • Prouver l'action native + la déflexion de volume + la trace d'audit.

Phase 2 — A1 désactivation leaver

  • MyPath leaver → routage groupe → approbation → clic « Disable » in-ticket → fan-out de tâches applicatives.
  • Dashboard : board de complétude + SLA de désactivation par site.

Phase 3 — B1 (immédiat) + B2 (digest dormants)

  • ADAudit : ticket immédiat « logon compte désactivé » ; digest hebdo « dormants » par site (patron send-hygiene).

Phase 4 — Corrélation & extension

  • Corrélation leaver→assets (récupération matériel) ; extension sécurité (groupe privilégié…) ; scorecard.

Rollback. Tout est additif et réversible : désactiver l'intégration / le profil d'alerte / le digest suffit. Aucune modification destructive d'AD, de SDP ni du dashboard. L'action AD reste toujours un geste humain approuvé — jamais une automatisation autonome.

10. Métriques de succès · Sources

  • Temps de désactivation leaver par site (SLA).
  • Volume reset/unlock déflecté (self-service + in-ticket).
  • Comptes dormants nettoyés par site (digest → action).
  • MTTA « logon compte désactivé » (signal sécurité).
  • % d'actions AD avec approbation + 2FA (preuve de gouvernance) ; 0 action AD hors ADManager Plus.
