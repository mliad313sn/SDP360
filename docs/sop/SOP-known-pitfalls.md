## Known Pitfalls

| Pitfall | Rule |
|---------|------|
| **Alertes SLA Teams : lire SDP en DIRECT, jamais `request_records` — et une URL de webhook est un secret (2026-10-03)** | `request_records` a jusqu'à ~1 h+ de retard (sync Analytics horaire) et n'a pas l'échéance de 1re réponse : toute alerte « bientôt due » calculée dessus arrive après le dépassement. Le poller lit `sdpApiClient.listOpenRequests()`. Une URL *Workflows* permet à quiconque de publier dans le canal : elle vit dans le secret `teams_sla_channels`, n'est jamais renvoyée au navigateur (`/api/teams-sla/settings` dit seulement `configured`) et est remplacée par `<url>` dans toute erreur. Les anciens « connecteurs entrants » Office 365 sont retirés : n'en proposer aucun. |
| **Une auto-référence de réunion DOIT porter le type de session — sinon une incubation écrase le PV du mois (2026-10-03)** | `saveMeeting` cherche d'abord une ligne par **référence** et met à jour celle qu'il trouve. La référence auto était `SITE_Dept_PV_AAAA-MM` pour TOUT : une incubation saisie sans référence, même site × département × mois qu'un PV existant, **remplaçait ce PV** (intake, priorités, enfants). `_buildReference` prend maintenant `intake_source` (`_INC_` pour `business_incubation`) — les 4 appels (sqlite + pg) le passent. Tout nouveau type de session doit avoir sa propre balise. |
| **`meeting.html` sert DEUX formulaires — un champ n'existe que dans un mode** | `#pvMain[data-mode]` + `[data-only="pv"|"inc"]` masquent des blocs entiers : un nouveau champ du PV doit porter `data-only="pv"` s'il n'a pas de sens pour une incubation, et réciproquement. Le blob incubation (`incubation_json`) ne s'écrit que par `state.incubation` dans la sauvegarde (ou l'import) — jamais par `saveMeeting` lui-même. En vérification locale : le `?v=` des assets ne change qu'au **commit** (`APP_VERSION` = SHA) → un JS modifié mais non commité reste servi depuis le cache navigateur. |
| **Un nom de site cherché à l'exacte casse = un site qui ne peut plus écrire (tracker 403, 2026-10-02)** | `sites.name` vaut `Hounde`, `Ity`, `Lafigue`, `Ouagadougou`, `ASSAFO`… alors que les tables de correspondance des modules mélangent `HOUNDE`, `Hounde IT Agents`, `Sabodala`. Toute traduction nom → code module passe par une fonction **normalisée** (casse, accents, suffixe « IT Agents ») : `inspection-db.siteNameToCode`, `tracker-db.siteNameToCode` / **`siteToCode(site)`** (repli sur chaque entrée du `zoho_group`). Ne jamais écrire `MAP[site.name]`. Tester avec les **11 noms réels de la prod** (`tests/tracker-site-code.test.js`). |
| **Lecture par rapport ou par site : le garde CENTRAL suffit — ne pas re-coder un contrôle de site par route (2026-10-02)** | `server.js` enregistre, juste après `requireReportSession`, un `app.get([_REPORT_ID_READ, _SITE_ID_READ], …)` qui refuse à un non-admin tout `GET /api/reports/<id>/…` dont le rapport n'est pas de son site, et tout `/api/reports/{monthly,yearly,objectives}/<site>/…` ou `/api/sites/<site>/…` d'un autre site. Une nouvelle route de lecture sous ces chemins est donc verrouillée **d'office** ; une route adressée autrement (par code de site, par groupe Zoho) doit appeler `_siteCodeReadDenied` / `_userSiteGroups`. Les ÉCRITURES gardent `_authorizeReportWrite` / `_authorizeSiteWrite` / `_sitelessWriteDenied`. |
| **`listReports` ne renvoie PAS de `site_id` (seulement `site_name`) — et un `site_id` falsy y supprime le filtre** | Un test qui vérifie `rows.every(r => r.site_id === …)` échoue sur du code correct. Et `listReports(undefined)` rend **tous** les sites : un non-admin sans site doit recevoir `[]` explicitement (`GET /api/reports` le fait). |
| **`window.__authUser` n'a ni `site_name` ni code de site** | Champs disponibles : `id, username, full_name, site_id, email, has_entra, role, roles, active`. Un verrou côté navigateur qui lit `u.site_name` ne s'applique **jamais** (c'était le cas du tracker jusqu'au 2026-10-02). Le périmètre vient du serveur : `/api/tracker/load` → `scope`, `/api/inspection/lookups` → `scope`, ou `site_id` + une liste de sites. |
| **Deux PV de test du même site × département × MOIS sont le MÊME PV** | `saveMeeting` retombe sur la référence `SITE_Dept_PV_YYYY-MM` : la deuxième sauvegarde **met à jour** la première (un PV « clos » redevient brouillon, un test passe pour de mauvaises raisons). Dans un test, un PV par mois. |
| **Lancer la suite dans un worktree donne ~64 échecs qui n'en sont pas** | Le worktree n'a pas de `.env` (« DASH_USER and DASH_PASS must be set ») et son `.git` est un **fichier** (`.git/last-deployed` introuvable pour `deploy-frozen-lots`). La vérification qui compte se fait dans le **checkout principal**. Pour les tests pg depuis un worktree, passer `PG_URL` à la seule commande — jamais l'exporter pour toute la suite (G-02). |
| **`SQLITE_IOERR_TRUNCATE` sous la suite complète = instabilité Windows, pas une régression** | Des dizaines de suites écrivent en parallèle dans des bases sqlite temporaires ; Windows refuse parfois une troncature. Relancer le fichier isolément (3 fois) avant de conclure. |
| **Les rôles mis en cache côté navigateur — `auth.js` les rafraîchit maintenant (2026-10-02)** | `report_user` (localStorage) était posé à la connexion et jamais relu : après un changement de rôle, la page appliquait les anciens droits jusqu'à 24 h. Le contrôle `/api/reports/auth/me` en arrière-plan réécrit le cache et recharge **une fois** par onglet si l'ensemble des rôles a changé. Ne pas retirer le garde `sessionStorage auth_roles_reloaded` (boucle de rechargement). |
| **Une extraction de source LF-only rend `''` sur tout checkout Windows — et les assertions NÉGATIVES passent alors à vide (2026-09-24)** | `core.autocrlf=true` est réglé dans la config **système ET locale** : tout l'arbre de travail est en CRLF alors que `git status` ne signale rien. Un `src.indexOf('\n}\n', start)` rend donc `-1`, la tranche dégénère en `''`, et chaque `assert.ok(!code.includes(…))` du fichier **passe sans rien vérifier** — les garanties que le test croit protéger ont cessé d'être contrôlées. Mesuré sur `public/reports.html` : `end('\n}\n') = -1` contre `end('\r\n}\r\n') = 284843` (2358 caractères de vrai corps). **Règle** : tout test qui lit un fichier du dépôt le normalise (`.replace(/\r\n/g,'\n')`) et passe par **`tests/_fn-source.js`**, qui **lève** au lieu de rendre une tranche vide. C'est la **2ᵉ occurrence** de cette classe (les goldens e-mail furent la 1ʳᵉ ; `.gitattributes` ne couvre que `tests/__golden__/*.html`). Pinné par `tests/fn-source.test.js`. |
| **Une suite « verte » peut n'avoir jamais exécuté la moitié PostgreSQL (2026-09-24)** | `tests/pg-helpers.js` : le défaut de `PG_ADMIN_URL` vise le cluster **Docker 5433** (absent de cette machine ; le vrai PG 17 écoute sur **5432**), et `sdp_app` n'a **pas** `CREATEDB` donc `PG_URL` ne peut pas servir d'URL admin. `provisionTestDb()` rendait `null`, les tests se déclaraient *skipped* **en silence**, la suite restait verte — **75 tests**, toute la parité pg (`pg-asset-followups`, `pg-report-asset-review`, `inspection pg`, `meetings pg`, `pgDb`…) **sur une prod 100 % PostgreSQL**. Depuis G-02 **ils tournent** (repli sur un **schéma jetable** dans la base de `PG_URL` — `sdp_app` en est propriétaire, aucun droit supplémentaire requis), le saut éventuel **dit pourquoi** (chaîne de connexion **mot de passe masqué**) et **`PG_TESTS_REQUIRED=1` en fait un ÉCHEC** : `PG_TESTS_REQUIRED=1 node --test --test-force-exit tests/*.test.js` avant tout déploiement touchant un fork pg. **Règle** : lire la ligne `ℹ skipped` — un `skipped` non nul n'est pas un succès. Fournir l'URL reste l'étape propriétaire (superutilisateur, ou un rôle dédié `CREATE ROLE sdp_test LOGIN PASSWORD '…' CREATEDB` — recette dans `tools/pg/README.md`). |
| **Une requête de catalogue dans un test pg doit être bornée à `current_schema()` (2026-09-24)** | Depuis G-02, une exécution pg s'isole dans un **schéma jetable de la vraie base** (et non plus dans une base jetable). Un `SELECT … FROM information_schema.tables WHERE table_name='users'` compte donc **deux** lignes : celle du schéma de test et celle de `public`. Quatre tests sont tombés là-dessus. **Règle** : toute requête sur `information_schema` ou `pg_indexes` dans un test pg porte `table_schema = current_schema()` / `schemaname = current_schema()` — ce qui est de toute façon l'assertion juste (« MON schéma contient ces tables »). Corollaire rassurant : le `search_path` ne contient QUE le schéma de test, donc une requête non qualifiée ne peut pas atteindre les vraies tables — elle échoue avec « relation does not exist ». |
| **Insérer dans `help.html` : vérifier l'EMPLACEMENT, pas seulement la présence (2026-09-24)** | Les entrées de sommaire de la section 18 ont été insérées **une ligne trop bas**, après le `</div>` qui ferme `<div class="toc">`. Elles sont devenues sœurs du sommaire ET du contenu : `.doc-layout` a gagné un **3ᵉ enfant**, la grille lui a donné une colonne, et le manuel s'est retrouvé écrasé dans un bandeau vertical. Le test vérifiait que les entrées **existaient**, jamais **où** — il est resté vert pendant que la page était inutilisable, et c'est parti en prod. `tests/help-assets-section.test.js` contrôle désormais l'appartenance au conteneur dans les deux langues. **Règle** : pour toute insertion dans une page à grille, asserter le conteneur parent (`closest('.toc')`, nombre d'enfants de `.doc-layout`) et regarder la page rendue. |
| **`db-backup.js` : la reprise anti-collision était du code mort → une SUPPRESSION pouvait être refusée (2026-09-24)** | Le nom de sauvegarde porte un horodatage **sans sous-seconde**, donc deux sauvegardes de la même base dans la même seconde entrent en collision. La reprise prévue pour ce cas testait `/file exists/i` alors que SQLite écrit **« output file already exists »** — qui ne contient pas cette sous-chaîne : la branche n'a jamais tourné. Comme `deleteInspection()` sauvegarde d'abord, une 2ᵉ suppression dans la même seconde **échouait** ; c'est la « flake connue » d'`inspection-blobs` que ce fichier documentait. Une sauvegarde existe pour **rendre** la suppression sûre, pas pour la bloquer. Pinné par `tests/db-backup-collision.test.js`. |
| **The COORDINATOR monthly send has NO arm flag — the scheduled task IS the switch (2026-09-23)** | Every other digest is gated by a `*_send_enabled` key in `reportConfig.DEFAULTS` (armed OFF), so a task that runs still sends nothing. `tools/reports/send-reports.js` (`--type=coordinator`, the monthly per-site report) has **no such flag**: it mails every site whose coordinator address is CONFIRMED as soon as the task fires. To hold it back you must disable or delete the `SDP-Report-coordinator-monthly` task (`schtasks /Change /TN <t> /DISABLE`) — unchecking something in the admin card will not do it. `--type=group` is the opposite trap: `SUPPORTED_TYPES = ['coordinator']`, so `group-weekly`/`group-monthly` run and exit with "not implemented yet" — the two tasks exist but send nothing. `node tools/pg/audit-sent-log.js` block [0a] lists every arm flag with stored-vs-default, which is why a key ABSENT from `report_config` must be shown as its DEFAULT rather than omitted. |
| **Scheduled report tasks MUST be created `/RU SYSTEM` — without it they NEVER run (2026-08-11 → 2026-09-21, prod)** | `services/reportSchedule.js` built `schtasks /Create` with no `/RU`, so each task ran as the account that created it — pm2's machine account `ABJ-SRV-012$` — in **"Interactive only"** mode. Nobody logs on to the server, so every `SDP-Report-*` task stayed `Ready` with Last Run `11/30/1999` and Last Result **267011** (never started): no scheduled report, weekly or monthly, ever went out. `_taskArgs` now adds `/RU SYSTEM` (pinned by `tests/report-schedule-task-args.test.js`), like the backup tasks in `Manage-SDP.ps1`. Existing tasks are fixed in place with `schtasks /Change /TN <task> /RU SYSTEM` (elevated) or by re-saving each schedule in the admin card. Check with `schtasks /query /tn <task> /v /fo LIST` → `Logon Mode` must not be `Interactive only`. |
| **A `tools/reports/*` CLI run standalone (Task Scheduler, manual `node …`) must load `.env` FIRST — otherwise it silently reads the frozen SQLite archives (2026-09-21)** | Every `*-db` module picks its backend (`*_BACKEND`) at require time, and only `server.js` loaded `dotenv`. The scheduled CLIs (`send-reports`, `send-weekly`, `send-hygiene`, `send-scoreboard`, `send-asset-group`, `send-asset-reminders`) and `backfill-asset-review` therefore read the July archives in prod when started on their own (found when the backfill dry-run listed W27 as every site's latest report). Each file now starts with `if (require.main === module) require('dotenv').config({ path: …/../../.env })` BEFORE any require; `tests/reports-cli-dotenv.test.js` enforces it for every file in `tools/reports/`. The `[Reports-DB] ✅ SQLite ready` boot line is printed UNCONDITIONALLY — it proves nothing about the backend; print `process.env.REPORTS_BACKEND` instead. |
| **Secrets never on a command line the installer builds** | Windows PowerShell transcripts and process listings capture command lines — the 4MyPeople installer transcript of 2026-09-15 leaked its PG superuser password exactly that way. In `tools/installer/`, passwords travel through `$env:PGPASSWORD`, environment variables (`SDP_APP_PASSWORD`; the pre-restore `PG_URL` in `Manage-SDP -Restore`) or a masked prompt; SQL that carries a password (`CREATE ROLE sdp_app ... PASSWORD`) goes through **`Invoke-PsqlSuperStdin`** (`psql -f -`, stdin) — `Invoke-PsqlSuper` (`psql -c`) is only for password-free SQL. The single exception is the EDB PostgreSQL installer's `--superpassword` argument in `Step4-Postgres`, reached only when no `postgresql*` service exists (fresh machine): EDB accepts nothing else, it is our child process, and the value is never logged. The env header prints secrets as `(set)` / `(not set)` only. Check with `grep -n "PASSWORD '" tools/installer/*.ps1` (must only hit the stdin call) and `grep -n superpassword tools/installer/*.ps1`. |
| **Asset engagement counts are FROZEN by the server — never trust client counts, never re-freeze on re-submit** | `PUT /api/reports/:id/asset-review` and the first `submitted` transition recompute `applicable`/`counts` from `getSiteAssetFollowups` (window = the report's Zoho week) and ignore whatever the client sent; a `submitted → submitted` call does not re-freeze. `saveReportAssetReview` writes ONLY the keys present in the patch (freeze vs notes can't clobber each other). "New hardware" = `asset_first_seen.baseline = 0` in the window and still present in `assets` — the first run after deploy is the baseline, so nothing is "new" that day. |
| **A cmd red screen must test for exit code EXACTLY 0** | `if errorlevel 1` means "≥ 1" and is FALSE for negative codes — `powershell -File <missing script>` returns **-196608** — so confirmations failed OPEN when the confirm script was missing or crashed. Use a `:confirm` subroutine that sets `CONFIRMED=1` only when `"!errorlevel!"=="0"` (delayed expansion) and treat everything else as refused. Also `set "ERRORLEVEL="` right after `setlocal`: an inherited environment variable named ERRORLEVEL shadows the real exit code read through `%errorlevel%`/`!errorlevel!`. Same rule in `_sdp_admin.cmd` option 6. |
| **Report section writers are DELETE+INSERT — on PG two CONCURRENT saves of one report DOUBLE every row (Lafigue W36, 2026-09-11); the PG forks now lock the report row, and any new section writer must too** | Under READ COMMITTED, tx B's `DELETE WHERE report_id=?` sees only the rows visible at its statement start: tx A's fresh INSERTs are invisible, so B "deletes" the already-deleted old rows (0) and INSERTs its own set → 14 infra KPIs instead of 7, **interleaved** WAN1/WAN1/WAN2/WAN2 because both sets carry `sort_order` 0..6 (the tell on the deck). Impossible under sqlite (better-sqlite3 serialises transactions) → it surfaced only after the PG cutover. Trigger = the page's two save paths: the 1.5 s **autosave** debounce and the manual **Save** button did not exclude each other. Fix: `_lockReportRowPg(H, id)` (`SELECT id FROM weekly_reports WHERE id=? FOR UPDATE`) opens `_saveInfraKpisPg` / `_saveLightsPg` / `_saveActionItemsPg`; the client's `saveSection` cancels the pending autosave timer, holds `_autoSaveBusy`, and queues itself behind an in-flight save. **Any new PG writer that DELETEs-then-INSERTs a report's children MUST call `_lockReportRowPg` first.** Reproduced then proven race-free with 20 parallel rounds on the dev PG; `tests/pg-reports-reports.test.js` carries the parallel test (skips without a CREATEDB admin). Rows doubled BEFORE the fix are repaired with `node tools/pg/dedupe-report-rows.js [--apply]` (dry-run by default; keeps the highest id per key = the later save; `action_items` deliberately excluded — fix those by hand in the editor). |
| **Every report/follow-up WRITE is authorised against the OBJECT's site via `_reportWriteDenial` — a valid session, or even the editor role, is NOT enough; a site-less profile is NOT global (audit 2026-09-05 F5)** | Rule for any new write route under `/api/reports/*`: call `_authorizeReportWrite(req, res, id[, {allowSubmitted}])` (or `_authorizeActionWrite(req, res, uid)` for a uid-keyed follow-up — it resolves the owning report through `rdb.getActionItemOwner`) BEFORE touching the DB. It returns the report or has already sent 404/403. The three checks: `editor` role · `user.site_id === report.site_id` unless `userHasRole(user,'admin')` (admin/executive/super_admin unscoped) · `submitted` frozen for everyone but super_admin (pass `allowSubmitted:true` only when the route has its OWN submitted rule, like `/status`). Never copy the old `req.reportUser.site_id && …` idiom — its short-circuit made a site-less editor global. Pinned by `tests/audit-report-write-auth.smoke.test.js`. |
| **`saveMeeting` UPSERTS `md_actions` by id — never go back to delete-all + reinsert; and an incubation is a DISTINCT session (audit F1/F2, 2026-09-06)** | Action ids are load-bearing: `md_action_updates` (audit trail, FK CASCADE), report follow-ups' `action_items.origin_id` (SP3 references) and the Site Actions hub all point at them. The client (`meeting.html`) round-trips `id` on every row; a row without id is INSERTed, a known id UPDATEd (`closed_at` kept if already closed, NULL if the status is non-terminal), ids absent from the payload DELETEd. `meetings-import.js` (bulk PV import) sends id-less rows → same net effect as before (documented "import wipes children"). The site×department×month fallback is **PV-only on both sides** (`_isIncubation(h)` guard + `COALESCE(intake_source,'') <> 'business_incubation'`): a PV never adopts an incubation row and vice-versa; only an identical `reference` updates an incubation. Reopening (issue or action, `addIssueUpdate`/`addActionUpdate`) clears `closed_at` — `_effClose` reads `closed_at` first, so a stale closure would silently drop a reopened issue from the overdue count (F4). Names imported from an incubation workbook are contacts, NEVER `*_signed_at` (F3). `commit({force:true})` skips error rows (F8). Pinned by `tests/audit-meetings-integrity.test.js` + the pg parity test. |
| **Route-smoke suites: force sqlite, use `tests/_http-fetch`, and log in with the role the route ACTUALLY requires — otherwise the suite goes red silently and STAYS red (2026-09-05 audit: 48 stale failures, some 3 weeks old)** | Three separate traps found in one audit. (1) The dev `.env` points every `*_BACKEND` at postgres, so any suite that boots `server.js` must set `process.env.<MODULE>_BACKEND='sqlite'` for all five modules BEFORE the first `require` — "REPORTS_BACKEND unset → sqlite default" is FALSE on this box; the symptom is `pgDb not initialised — await initPgReports() at boot`. (2) The global `fetch` is undici; its keep-alive sockets trip a libuv assertion (`UV_HANDLE_CLOSING`, `src/win/async.c`) when `--test-force-exit` tears the process down on Windows — every subtest passes, then the FILE is marked failed, non-deterministically across files. Use **`const fetch = require('./_http-fetch')`** (core http, `agent:false`, fetch-shaped: status/ok/headers.get/text/json/arrayBuffer) — every smoke file does now. (3) When a route's gate changes (admin settings → `requireSuperAdmin` on 2026-08-16, IT Review → executive on 2026-08-31), the smokes that log in as `admin` start returning 403 and nobody notices because the suite already had "known" failures. Rule: after touching a gate, grep `setUserRoles(me.id, ['admin'])` in `tests/` and promote the suites that hit that route. Corollary of all three: **a suite with "known pre-existing failures" is worthless — keep it at 0 red** (it was 1783/0 on 2026-09-05). Fixtures for `upsertRequestBatch` must carry EVERY named column (`template` was missing → `RangeError: Missing named parameter`). |
| **WAN SLA (chargeback) = event-log Meraki (coupures TOTALES), PAS la dispo dérivée ; dispo mesurée DANS l'horaire de service ; notif ISP ARMÉE-OFF ; attribution STOCKÉE, pas recalculée par le moteur** | L'instrument SLA/refacturation ISP (`services/wanSla.js` + `wan_outages` + poller/ingester) est **séparé** de WAN Health et de `wan_link_snapshots` (ne les touche pas). **La dispo qui compte pour les 97 % = les coupures totales** (uplink `failed`, poller `orgUplinkStatuses` / event-log) — c'est le Niveau 1 du contrat (interruption totale). **Deux instruments, deux réponses, par design (confirmé 2026-09-04)** : Sabodala wan2 est *dégradé* (17-21 % de perte, MOS 1,86) mais n'est JAMAIS passé `failed` → 0 coupure au SLA (contrat sans clause de dégradation — décision user 2026-09-05 : on laisse) alors que la dispo dérivée calibrée (Santé & Qualité) le lit à ~20 % comme Meraki. Ne pas "réconcilier" les deux. Chaque coupure est **découpée sur le calendrier d'horaire-service** du circuit (`clipToService`, 2 fenêtres/jour, mine 7j/bureau 5j, GMT — hard-constraint V1) → une coupure nuit/week-end (bureau) compte 0. **`clock_start='notification'` par défaut** (contrat notification→rétablissement ; la figure `detection` n'est que la borne haute objective) ; une coupure <15 min ne compte jamais. Crédit = **paliers % du MRC** (inclusif `>=`, 95,0 %→palier 95), montant texte+devise **sans glyphe**. **⚠ Confirmations d'intégration** (comme la calibration) : les strings d'événement Meraki (`wan_1_down`…) sont **config-driven** (`event_types`) et le contrat de pagination `networkEvents` (`endingBefore`/`pageStartAt`) sont à valider contre l'org réel ; le balayage de récupération du poller est org-wide (un device omis d'un poll fermerait à tort son incident — à durcir). **Non-goals** : SLA réponse helpdesk (info 30min/feedback 8h → Phase 2), Niveau 2/3 dégradé, Insight, sites non-UTC. |
